# Changelog

## 0.2.0 — unreleased

- Add Windows stock OpenUSD debug SDK provisioning, native qualification and configuration-specific packages for debug hosts.

Changes that ship in ovlive 0.2.0.

### What ships

- Release targets add stock USD 25.11 on Linux aarch64 and Windows x86-64, so the release carries a stock and a Kit USD 25.11 package for each of Linux x86-64, Linux aarch64 and Windows x86-64, all with Python 3.12, and Kit's lock pins the stock packages as `kit_omni_usd_live_openusd_<platform>`. The Kit bootstrap accepts a `stock-25.11` package on Linux and Windows hosts that loaded stock OpenUSD 25.11, and only `kit-25.11` on macOS.

### Transport

- ovlive links gRPC 1.83.1, c-ares 1.34.9, protobuf 5.29.5, abseil 20250127.0 and re2 20250722. With gRPC 1.65.4 and c-ares 1.34.8, a Windows process aborted on its first DNS lookup through ovlive (`grpc_polled_fd_windows.cc:227`, [grpc/grpc#37969](https://github.com/grpc/grpc/issues/37969)). gRPC 1.83.1 also fixes [GHSA-hf3w-6hpw-qp67](https://github.com/grpc/grpc/security/advisories/GHSA-hf3w-6hpw-qp67) (High: unbounded memory from decompression, GOAWAY debug data and fragmented HTTP/2 DATA frames a server can send), and c-ares 1.34.9 the eleven advisories against 1.34.8, including the High [GHSA-wpr3-8q3r-4q8c](https://github.com/c-ares/c-ares/security/advisories/GHSA-wpr3-8q3r-4q8c) (memory corruption when a lookup is cancelled after a connection failure); protobuf, abseil and re2 move to the versions gRPC 1.83.1 builds against. On Linux the gRPC closure is the GCC build, as the client is. The `runtime-foundation` suite resolves an endpoint's hostname through a loopback DNS server on every platform.
- A read stream frame over `SubscribeReadLayer`'s per-method message limit ends the read `RESOURCE_EXHAUSTED`, the status gRPC 1.83.1 reports for it; gRPC 1.65.4 reported it as `CANCELLED`.
- A release archive fails its check when any member carries a PEM certificate, so the package never ships a CA store of its own, such as the `roots.pem` the gRPC package carries; ovlive trusts the CA PEM its host supplies or the system store.

### Authoring and consistency

- A same-parent rename onto a name another sibling holds deletes that sibling with its subtree first, as a Create at that name does and as Nucleus and Kit's applier do, on every reader, in the journal's replay of a pending rename and in the reference service by default; a rename to the section's own name changes nothing. Two siblings with one name arise only from a service that keeps both, and the lower section ID shows ([design section 10](docs/ovlive-design.md#10-concurrent-edit-semantics-and-known-limitations)).
- A Move to another parent onto an occupied slot whose occupant's listed subtree holds the moved section through a stale children list deletes both and applies the rest of the update, as a same-parent rename onto such an occupant does; when that subtree holds the new parent instead, the moved subtree is deleted with it, as a Move to a missing parent is. Both apply on every reader, in the journal's replay of a pending Move and in the reference service; ovlive 0.1.0 rejects the whole update ([design section 10](docs/ovlive-design.md#10-concurrent-edit-semantics-and-known-limitations)).
- A Create, or a Move to another parent, collides only with siblings of its own child list, so a prim `x` and a property `x` of one prim coexist, as Kit's applier and USD allow, while a Create or Move into a slot of its own child list still deletes the occupant with its subtree, so the last writer wins. Every reader, the journal's replay of pending intents and the reference service apply the rule ([design section 10](docs/ovlive-design.md#10-concurrent-edit-semantics-and-known-limitations)).

### Compatibility with the live edit service

- The deployed live edit service and ovlive 0.1.0 keep both siblings of a same-parent rename onto an occupied name until the service adopts the rename cascade. Until then a reader that applies such a rename as it commits holds one sibling where the service holds two, and a reader that opens the layer afterwards shows the lower section ID; no layer fails ([support boundary](docs/ovlive-support-boundary.md#known-limitations)).
- The deployed live edit service and ovlive 0.1.0 collide on (parent, name) whatever the spec type until the service adopts the rule. Until then a reader that applies such a Create or Move as it commits keeps both sections where the service keeps the later one, and a reader that opens the layer afterwards holds only the later one; no layer fails ([support boundary](docs/ovlive-support-boundary.md#known-limitations)).
- Live Edit 0.1.x delivers again, after a catch-up it cannot prove at a stable cut, commits the catch-up holds; a delivered rename, like a delivered Create or cross-parent Move, whose name a later commit gave to another section deletes that section on a reader that opens the layer. Live Edit 0.2.0 never delivers an edit twice ([support boundary](docs/ovlive-support-boundary.md#known-limitations), [design section 12](docs/ovlive-design.md#12-stream-ordering-coverage-and-reconnect)).

### Status and diagnostics

- A `Cancel`, `LeaveSession` or `UnregisterCallback` that returns `TIMEOUT` after a nonzero timeout emits a `cleanup_timeout` warning (code 38) naming the call and its handle, and the snapshot's `cleanup_duration_ms_by_call_result` metric counts every result of those calls, `ReleaseRequest` and `UnregisterEndpoint`, `BUSY` refusals and zero-timeout polls included, as the shutdown metrics count runtime shutdown. A diagnostic sink's own unregistration records to history only. The event and metric group are additive within catalog and diagnostic schema version 1 ([diagnostic catalog](docs/ovlive-diagnostic-catalog.md#cleanup-timeouts)).

### Kit integration

- Kit 111 hosts: on Linux the bootstrap accepts a `stock-25.11` package when the Kit process loaded stock OpenUSD 25.11, and a `kit-25.11` package only when it loaded Kit's `ov`-namespace USD. Kit 111's USD namespace shim, a `libov_25.11usd_ms.so` that links the stock libraries, counts as stock; any other `ov`-namespace library next to stock USD, or one that cannot be verified, refuses startup. macOS accepts `kit-25.11` only. The extension starts at order -100, so the `live` resolver registers before OpenUSD's first resolver use ([Kit guide](docs/ovlive-kit.md#what-works-with-a-public-kit-build)).
- Kit 111 hosts on Windows: the bootstrap reads the Kit process's loaded modules and accepts a `stock-25.11` package when it loaded stock OpenUSD 25.11 (`usd_sdf.dll`), and a `kit-25.11` package only when it loaded Kit's `ov`-namespace USD (`ov_25.11usd_ms.dll`). An `ov_25.11usd_ms.dll` beside stock USD counts as stock only when its loaded image imports `usd_sdf.dll`, as the namespace shim's does; any other, or one whose image cannot be read, refuses startup ([Kit guide](docs/ovlive-kit.md#installation)).
- The extension's shutdown hook gives a started host five seconds to stop its threads, so a Kit session that used no live layers exits without the `Live Services shutdown incomplete: TIMEOUT` error when the host stops within that time, as an idle host does (about 65 ms on Kit 111); a host with live layers, catalogues or session roots still attached answers `BUSY` at once, as before, while joined sessions are left and in-flight requests drained within the five seconds ([Kit guide](docs/ovlive-kit.md#usage)).

## 0.1.0 — experimental

The first experimental release of ovlive: Omniverse Live Services layers as ordinary USD layers, from one C++ runtime that a host loads as a USD plugin. The [support boundary](docs/ovlive-support-boundary.md) states what is supported and which qualification gates are open.

### What ships

- A macOS arm64 development build uses pinned stock OpenUSD 25.11, source-built transport libraries and Python 3.12. Mach-O packaging, dylib loading and direct package checks preserve the single runtime and SDK identity requirements. macOS arm64 is the fourth foundation/component CI platform, with bounded process-group cleanup and four recorded detached-process test exclusions. Its SDK build caches pinned SDKs by recipe and toolchain identity and revalidates installed hashes and native loading; its package build runs ten direct component/package/sample CTests plus staged load-order checks. The standalone qualification entry point retains its profiles and worker configuration. Direct Mac test-runner admission is limited to foundation and the URI, wire-envelope and lock-noalloc SDK-free suites; SDK-dependent and reference-service suites require Linux/Windows descendant-tree containment. Mac release qualification and detached-process supervision remain open.

- Public distribution is source only; native release publication requires the approved NVIDIA repository identity and enterprise-internal visibility, rechecked at every remote publication mutation and public packman staging is disabled. NVIDIA OMPF schema copies carry Apache-2.0 headers with original/current provenance hashes, and the LiveService proto is the live edit service's file unchanged, with its own Apache-2.0 header; LICENSE is canonical Apache-2.0, SHA-256 retains MIT and Allan Saddi BSD-2-Clause notices.

- One C++ runtime in the `omni_usd_live` library serves the USD `.live` file format and `live://` resolver, the `omniUsdLive*` C API and the `omni.usd.live` Python API.
- Release targets are Kit USD 25.11 on Linux x86-64, Linux aarch64 and Windows x86-64, and stock USD 25.11 on Linux x86-64, all with Python 3.12. Each target ships one packman package with a path-free manifest, packed from the reproducible native archive its qualification checked ([release procedure](docs/ovlive-release.md)); it is not signed.
- NVIDIA-owned source is licensed under Apache-2.0, with third-party attribution and notices preserved.
- The source archive holds the client under `client/`, beside the license, notices, governance documents and workflows the repository's parts share at its root.

### Authoring and consistency

- Live layers are in-memory only: a host opens each one with `FindOrOpen` or `CreateNew` on its publication context and then inserts it into a stage, and no sublayer, reference or payload in loaded or saved content names a live URI. Composing an unopened live URI is unsupported; USD's warning for each sublayer it then fails to load says to open live layers on the host before composing them ([design section 1](docs/ovlive-design.md#1-purpose-audience-and-scope)).
- Live layers are authored with plain USD on a host-owned serial dispatcher. A rejected write, or one whose outcome cannot be resolved, fails the layer and keeps its edits for `SdfLayer::Export` and reopen ([design section 13](docs/ovlive-design.md#13-mutation-outcomes-retry-policy-and-recovery)).
- Edits are encoded as the service persists them: animation as per-time sample records and child membership and order through sections, so a fresh service snapshot reproduces the authored content. A whole time-sample map edit erases the keys its writer saw and keeps a peer's concurrent keys.
- A pending edit the service will predictably reject, a Create of an identity a peer created first, is left out of the visible scene and of an export, the peer update that conflicts with it applies, and the layer fails with the service's `INVALID_ARGUMENT` whichever of the two arrives first. A pending Reorder naming a child a peer has since removed or moved ignores that child and orders the rest by the same rule, as a service that orders lists per child list commits it; a service that stores lists verbatim rejects it instead, which fails the layer the same way ([design section 10](docs/ovlive-design.md#unresolved-conflicts-fail-the-layer)).
- Writers that each author content under ancestors the layer lacks keep it when their ancestors collide. An ancestor a writer creates only as an `over`, as `SdfCreatePrimInLayer` does, is an implicit container; when a peer's later Create at its path replaces it, the writer that created it restores the container's content under the peer's section with ordinary new writes, in the transaction that applies the replacement, so its own scene never loses the content, and a writer restores the content its pending writes create under any replaced section. A child the peer's section already holds stays; implicit containers merge, and an authored prim keeps its specifier, `typeName` and other prim fields over an implicit container at its path in either commit order, its restore writing them onto the container. A restore refused for capacity waits and retries; more than 32 restore rounds of one subtree, or a restore no admission can ever fit, fails the layer with `RESOURCE_EXHAUSTED`, keeping the content for export. Concurrent creates of one authored prim stay last-writer-wins; an authored prim that a peer's implicit container replaces restores its prim fields and children onto that container. The `first-create` writer campaign scenario checks every writer's content on every writer and a late joiner ([design section 10](docs/ovlive-design.md#10-concurrent-edit-semantics-and-known-limitations)).

### Compatibility with the live edit service

- Content restores use only Creates and field and sample records, so clients of every version converge in one session; a writer on 0.1.0, which has no restore, loses the content under its own implicit containers when another writer's Create replaces them ([support boundary](docs/ovlive-support-boundary.md#supported-configuration)).
- The reader accepts every catch-up shape the service sends: compacted snapshots that keep erased fields as empty values, commits delivered again after a snapshot without a proven stable cut, reconnect diffs that restate sections at their current sibling index, values of types outside the shared table that Kit writes as type 0, and empty commits, which the service delivers as an empty diff at their sequence; the reader also accepts a header-only frame or a skipped position for one.
- An incoming Reorder applies its list to each child list it names exactly as USD's `SdfApplyListOrdering` does, per child list, as the live edit service does: a prim order moves only prims and a property order only properties, each within the positions its list holds among the parent's children; a partial list orders the children it names as USD orders a partial list; and IDs that are not children, and every repeat after an ID's first occurrence, are ignored. Every child is kept; a service that stores the list verbatim keeps only the listed children, so its late joiners can see fewer than a live reader ([design section 9](docs/ovlive-design.md#child-lists)).
- A session message over the service's 4 MiB stream limit is refused locally rather than lost, and a read the service ends with `INTERNAL` reconnects.
- Every session join opts in to the live edit service's client keepalive, and when a join's Connected reports a non-zero keepalive interval the session's worker sends an empty keepalive after a full interval in which no write on the stream finished, so a peer whose network went silent leaves presence instead of lingering. A keepalive never preempts a write, takes no request or queue slot, and an active session sends none; a join whose service reports a zero interval, as when the service has the keepalive disabled, sends none. A join the service ends for a keepalive timeout rejoins with the reconnect backoff ([design section 15](docs/ovlive-design.md#15-sessions-presence-and-messages)). The keepalive fields are placeholders until the service's schema change lands.
- Layer reads and session joins reconnect with their own backoff, tuned for service restarts and outages and separate from the unary retry options: attempt *n* waits uniformly in [0, 2 × min(`reconnect_maximum_ms`, `reconnect_initial_ms` × 2^(*n*−1))), drawn per layer or session so the layers of one process spread, and `reconnect_max_attempts` consecutive failed attempts fail the layer or session with `UNAVAILABLE`. The defaults of 1 s, 60 s and 10 attempts ride out an outage of about five minutes on average ([design section 12](docs/ovlive-design.md#reconnect)).
- A layer-read attempt that the service accepts but does not answer within `initial_open_timeout_ms` ends `TIMEOUT` and counts as a failed reconnect attempt, so a stalled reconnect resumes or fails the layer `UNAVAILABLE` with its edits kept; a read past its first complete response has no deadline ([design section 12](docs/ovlive-design.md#reconnect)).
- An update or creation seed over the live edit service's entry limits is never sent. The runtime counts each one as the service does, its struct commands, set fields and time samples together against 99,999 and each child reorder's list against 100,000. A host turn over them is never split: like a turn over the 65,536-operation limit, it fails the layer with `RESOURCE_EXHAUSTED`, a USD runtime error names the counts, and the host content keeps every edit for `SdfLayer::Export`. A seed over them fails its `Export` or `CreateNew` before any `CreateLayer`. A service refusal that arrives anyway, `DELTA_TOO_LARGE` or `CHILDREN_LIST_TOO_LONG`, puts its reason and counts in the `rpc_failed` diagnostic ([design section 8](docs/ovlive-design.md#quotas)).
- Every layer write and creation carries an operation ID. When its reply is lost on an endpoint whose `Ping` reports that it honours operation IDs, the runtime re-sends it once with the same bytes and ID instead of failing the layer, and the service answers with the original commit, so a single transient failure does not stop a client from editing the layer. On a server whose `Ping` does not report operation-ID support, which includes 0.1.x Live Edit deployments, nothing is re-sent and a lost reply fails the layer with its edits kept. A re-send can still apply a write twice during a rolling upgrade of the service, when a replica without the support loses the reply, and after a disaster-recovery restore of the service ([design section 13](docs/ovlive-design.md#the-single-operation-id-re-send)). The re-send of an unchained write, as on an endpoint that does not chain writes, goes out at once, but the layer issues no later write until the first attempt's `request_timeout_ms` deadline plus 5 s has passed, because the service may still run that attempt and could apply it after the next write; a `retry_scheduled` record with reason 4 reports the hold.
- An `UpdateLayer` the live edit service refuses `UNAVAILABLE` with its `google.rpc.ErrorInfo` (domain `nvidia.omniverse.live.v1alpha`), which marks a refusal that applied nothing such as an upload admission refusal, reports `UNAVAILABLE` rather than `OUTCOME_UNKNOWN`: the write keeps its place in the FIFO and is issued again with the same bytes, operation ID and client ID after a backoff: the reconnect schedule's draw, or the refusal's `google.rpc.RetryInfo` delay when that is longer, with no jitter added to the delay, capped at `reconnect_maximum_ms`. After `reconnect_max_attempts` consecutive refusals the layer fails `UNAVAILABLE`, and each backoff is a `retry_scheduled` record with its delay and source. A plain `UNAVAILABLE` stays `OUTCOME_UNKNOWN`.
- A `CreateLayer` the live edit service refuses `UNAVAILABLE` with its `google.rpc.ErrorInfo`, such as `EXT_RELEASE_BUDGET_FULL` while the store's external-value cleanup is backed up, applied nothing and is issued again with the same seed bytes and operation ID after the same backoff as an `UpdateLayer`, within the initial-open deadline, so a creation seeded with large values waits out the backlog instead of failing its open. After `reconnect_max_attempts` consecutive refusals the creation fails `UNAVAILABLE` with its seed kept, and each backoff is a `retry_scheduled` record with operation `CREATE`. A creation refused without that `ErrorInfo`, or with `INTERNAL`, is not reissued ([design section 13](docs/ovlive-design.md#the-reissue-after-a-refusal-that-applied-nothing)).
- A host can ask for an advisory merge-owner lease on a session join, so that among the instances that opt in only one may merge: a join with `OMNI_USD_LIVE_JOIN_MERGE_OWNER` (Python `merge_owner=True`) sends `CLAIM`, `RELEASE` and `VERIFY` with `omniUsdLiveRequestMergeOwner`, receives `MERGE_OWNER` events for each owner change,, claims again after a reconnect and whenever the lease it still wants falls free, and reads its view from `omniUsdLiveGetMergeOwner` (Python `Session.merge_owner`); `SessionCatalog.can_merge` keeps its static creator rule. It fails open: a join that did not opt in, or whose service does not negotiate the lease, gets `UNSUPPORTED` and keeps the static creator rule, and only an opted-in join can receive the new response frame. The protocol fields are placeholders added ahead of the live edit service's change, and the lease is qualified only against the reference service ([design section 15](docs/ovlive-design.md#15-sessions-presence-and-messages)).
- The LiveService protocol is the live edit service's own `live_service.proto` at its main commit `13a30991`, under the `live.proto` name, with the agreed client keepalive fields, the merge-owner lease fields and the chained-writes extension added ahead of the service's own changes ([provenance](source/live/protos/README.md)).

### Performance and limits

- On an endpoint whose `Ping` advertises operation IDs and chained writes, a layer keeps several writes in flight instead of one: each sends its predecessor in the writer's chain in a `ChainedUpdateLayerHeader`, so the service commits them in order, and the window starts at 8, grows to at most 16 while writes are acknowledged and halves on a refusal that applied nothing. A lost reply or a refused write mid-chain cancels the chained calls behind it, which wait at the service for it and so apply nothing, and is re-sent at once with the same IDs and `no_wait`, so the service commits it, answers `ALREADY_COMMITTED` or names the chain's latest write (`last_record`, `last_operation_id`); every write commits exactly once, in order, instead of failing the layer `OUTCOME_UNKNOWN`, which remains only when the chain names a write this writer never issued, as after the service loses its operation records. While a write's outcome is unknown the layer's read stays closed and the write is first settled through the chain. A write the chain proves committed without a reported position is placed by no inference: the read is resubscribed from the coverage frontier, its catch-up applies in service order, this writer's commits included, and the write's pending intent retires when its proving write applies. An acknowledged or chain-proven write that a resumed read's net-empty catch-up passes retires without applying its bytes, since the service's net result already accounts for it. Recovery from a lost reply costs one extra round trip before peers' edits arrive; the steady state is unchanged ([design section 12](docs/ovlive-design.md#settling-uncertain-writes-before-the-read-resumes)). A chained write answered with a status that does not settle the call, such as a plain `RESOURCE_EXHAUSTED` or `PERMISSION_DENIED` without the service's `ErrorInfo`, is settled the same way instead of failing the layer with that status: it ends committed, with the typed result of a later answer that settles it, or `OUTCOME_UNKNOWN` when the chain's re-sends run out. A chained call refused `INVALID_ARGUMENT` without an `ErrorInfo` of the service's domain came from a replica that does not know the chained header and applied nothing: the endpoint's writes are then sent unchained, each once every chained call of it or an earlier write is settled, writes whose chained calls ended unsettled (a cancellation, a deadline, a plain `UNAVAILABLE` or another status without the service's `ErrorInfo`), which the service may still commit later, being first finished through the chain with `no_wait`, while later chained calls stay in flight; with that `ErrorInfo` (`INVALID_UPDATE`) the refusal is definitive. Admitted writes never exceed the window, one write on an endpoint without chaining, and at most one waits to be issued: otherwise host turns coalesce into one update of every whole turn since the last, compiled once when a write is issued or settles, and split before a compile limit is crossed. The protocol fields are agreed with the live edit service team and vendored ahead of its own change, to be reconciled when the service and its proto move into this repository ([design section 13](docs/ovlive-design.md#chained-writes)).
- Layers of any size the service holds open and update. A read is bounded by the endpoint's pending-byte budget (`max_pending_bytes_per_endpoint`, default 1 GiB), an update the layer sends by `max_update_bytes` (default 100 MiB, the service's upload limit), and the journal's work budgets grow with the layer. A host turn or peer update that edits fields, dictionary keys and time samples costs work in proportion to its records and the specs they address, with a logarithmic factor in the layer's size: successive scenes, host captures and the compiler's replay store share their unchanged specs and index structure, and publication compares only what changed. A host turn or peer update that creates, removes, moves, renames or reorders specs costs the subtrees it moves and the children lists of the parents it changes ([design section 8](docs/ovlive-design.md#capture-and-flush)).
- A backlog of peer updates applies in batches of up to 64 consecutive updates, within `max_update_bytes` beyond the first, each batch with one scene build, one derivation of the visible scene and one host publication. A batch that grows a layer by more than its replay work budget can fail with `RESOURCE_EXHAUSTED` where the same updates applied one at a time would not ([design section 12](docs/ovlive-design.md#ordered-application)).
- A pending local edit is charged for its own bytes and operation log, not for copies of the layer, so the pending-byte charge of unconfirmed edits grows with their number and size, not with the layer ([design section 8](docs/ovlive-design.md#quotas)). Admitting a local edit, applying its acknowledgment and applying a peer update that sets only fields and samples cost work in proportion to that edit or update alone, as above, never to the number of pending edits, so draining a backlog of pending edits costs work linear in its length; a structural peer update replays all pending edits in one pass onto one working scene, materialized once ([design section 8](docs/ovlive-design.md#authoritative-visible-and-host-state)).
- A frame may author as many change blocks as memory allows: the host edit buffer is bounded by bytes, not records, with every layer's buffer on an endpoint sharing a budget of `max_pending_bytes_per_endpoint` that is separate from transport reservations, so an endpoint can retain about twice that value plus one started host turn per layer. A host turn is refused with `RESOURCE_EXHAUSTED` only once the endpoint's buffered bytes reach the budget, with a USD runtime error naming that bound, and the flush after the frame sends the buffer as several updates of whole change blocks within every compile limit. A single change block over a compile limit still fails the layer ([design section 8](docs/ovlive-design.md#quotas)).
- A flush that edits only fields skips namespace planning, and a flush or peer update that creates many specs plans and builds in time linear in the specs it creates, with a logarithmic factor in the layer, not in the layer's size times the number of created specs.
- Applying an update's time samples and compiling a flush's sample writes cost work linear in the number of samples, so an update or a flush that animates one attribute with many keys compiles within the default work budgets: an incoming update of 99,999 samples on one attribute and a flush of 65,536 sample writes to one attribute both apply.
- A flush that writes one field, dictionary key or time sample many times emits one record of its last value, and the 65,536-operation limit counts those writes once, so coalesced host turns that rewrite the same attributes compile to one small update; a turn of more than 1,048,576 operations, counting every write, fails the layer with `RESOURCE_EXHAUSTED` before it compiles; the pending edit still retains every original write ([design section 8](docs/ovlive-design.md#capture-and-flush)).
- A host turn's field writes cost fewer path comparisons through capture, compilation, verification and the scene builds of admission and acknowledgment: each lookup or edit of a scene index descends it once, a changed spec's storage is replaced in one edit, verification reads each spec once per store and looks each of its fields up by name, so verifying a spec costs work linear in its fields, and a flush that rewrites the same attributes many times measures each path once and skips the replay of writes a later write of the same field replaces.
- A peer update, a batch or a layer's own publication that changes the visible content sends USD per-path notices rather than a whole-content replacement, so a `UsdStage` resyncs only the paths a change creates, removes or moves and treats a field edit as info-only; only a layer's first installation replaces its content. Fields compare by representation, so a zero that changes sign, in a value or a time-sample key, or a layer offset within USD's comparison tolerance is a change and the host content stays exactly the visible scene; a publication with no difference, such as the acknowledgment of the layer's own edit, leaves the host content as it is ([design section 7](docs/ovlive-design.md#7-host-concurrency-and-scheduling-contract)).
- Each endpoint keeps at most `OmniUsdLiveRuntimeOptions.max_calls_per_endpoint` gRPC calls open on its connection, 1,024 by default, a client-side budget (the live edit service enforces no per-connection limit), so a process's open calls stay bounded whatever the server allows, and gRPC never queues a call with its deadline running behind a server or proxy stream limit at or above the budget. Open layers and joined sessions hold one of 896 stream units each, across reconnects, until the layer closes or fails or the session leaves, and a layer open or join past them fails `RESOURCE_EXHAUSTED` at once, before any RPC; layer writes and finite requests share the other 128 and wait for one on the client in FIFO order, so issuance windows shrink under contention and a waiting write never times out or becomes `OUTCOME_UNKNOWN`. A `call_budget_exhausted` warning (code 37) reports each refusal and wait. The option is appended within ABI 1.0, which accepts the shorter record, and nothing changes on the wire ([design section 4](docs/ovlive-design.md#concurrent-calls)).
- The default `request_timeout_ms` is 35000 ms, above the Live Edit service's 30 s request timeout, so a layer write's deadline outlasts the service's internal retries before a lost reply is re-sent ([reference](docs/ovlive-reference.md)).

### Status and diagnostics

- The diagnostic snapshot's `layer_writes` metrics report writes in flight, the issuance window, chain re-sends and the host edits each update holds, and a `retry_scheduled` record with reason 3 reports each resolved break of a layer's write chain ([snapshot schema](docs/ovlive-diagnostic-schema.md#layer-writes)).
- Typed operational status and callbacks, and bounded diagnostics validated against a schema and event catalog. The Python `copy_diagnostics()` and `export_diagnostics_json()` return every retained history record unless `max_records` limits them, as the C API's NULL export options do.
- A layer that falls behind its peer stream stays `READY` but shows it. `OmniUsdLiveStatus` carries its `read_sequence` and `applied_sequence`; an `apply_lag_entered` warning fires once the applied sequence trails by more than `OmniUsdLiveRuntimeOptions.apply_lag_warning_threshold` positions (default 256) beyond the catch-up target, and `apply_lag_exited` once the lag falls to half of it; and `metrics.apply_lag` records the layers lagging, its high-water mark and every installed peer update's receive-to-apply time. The status and option fields are appended within ABI 1.0, which accepts the shorter records ([design section 17](docs/ovlive-design.md#17-operational-status)).
- A writer whose first-created section a peer's later Create at the same path replaced reports it: a `section_replaced` warning record (code 36) carries the section ID and the replacing commit's sequence, and a USD warning on the host names the layer and path ([diagnostic catalog](docs/ovlive-diagnostic-catalog.md#replaced-sections)).

### Kit integration

- The `omni_usd_live` Kit extension declares `omni.kit.live_services`, its bootstrap, and then `omni.usd.live` as Python modules, so Kit's API checker accepts `omni.usd.live` as a public module; the bootstrap's package, ABI and plugin checks run before the native binding is imported, and a second start of the extension in one Kit process fails and asks for a Kit restart ([Kit guide](docs/ovlive-kit.md#python-modules-and-startup-order)).
- The `kit-reference` lane qualifies a released packman package with `--kit-release-package`: it verifies the zip against its checksum and release manifest, requires the unpacked folder to hold exactly the manifest's files, and checks the module Kit loads ([Kit guide](docs/ovlive-kit.md#validating-a-released-package)).

- The independent reference service, whose graph profile covers the value families Kit's presence layer authors, seeded many-writer campaigns, and a test runner for Linux and Windows ([testing guide](docs/ovlive-testing.md)).

- On Windows the samples and native test drivers write each record when they produce it, since the C runtime's exit-time flush of buffered `stdout` can be skipped while other threads are still exiting; a host on Windows flushes the output it needs before it exits.
