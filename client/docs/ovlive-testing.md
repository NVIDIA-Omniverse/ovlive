# Testing guide

This guide explains how ovlive is tested: the test runner and its suites, what each layer proves, the independent reference service and oracles that judge results, the rules every test follows, and the qualification gates the lanes feed. It is for engineers and agents who run tests, add one, or read a failure. The [build guide](ovlive-build.md) builds the binaries the suites consume, the [CI guide](ovlive-ci.md) runs them on a provisioned worker, and the [support boundary](ovlive-support-boundary.md) states what the lanes cover today and what is open.

Commands in this guide run from the repository's `client` directory, and the paths they name are relative to it; build output and evidence go to `../.cache`, the `.cache` directory at the repository root.

## Running the tests

`tools/live/test.sh` runs `tools/live/test.py`, the entry point for every suite, with the interpreter that `LIVE_TEST_PYTHON` names (default `python3`). `tools/live/test.bat` is its Windows counterpart. Linux and Windows use descendant-tree guards; macOS admits only `foundation`, `uri`, `wire-envelope` and `lock-noalloc`, using bounded process-group cleanup and a foundation inventory with four explicit detached-process exclusions. SDK-dependent and reference-service suites require Linux/Windows descendant-tree containment; direct macOS package checks use [macos_ci.py](../tools/live/macos_ci.py). Other platforms run no suite and report an infrastructure error (`platform`). It never downloads a dependency; every binary and interpreter is an explicit input whose build manifest and source identity the runner validates first.

```sh
./tools/live/test.sh --list
./tools/live/test.sh --suite foundation --seed 42
./tools/live/test.sh --replay ../.cache/live-tests/run-EXAMPLE/replay.json
```

`--suite` takes a comma-separated list; the default is `foundation`. The suites are:

| Family | Suites | Required inputs |
| --- | --- | --- |
| Python harness | `foundation`, `uri` | None for `foundation`; `--uri-library` for `uri` |
| Native components | `lock-noalloc`, `wire-envelope`, `usd-values`, `wire-scene`, `scene-journal`, `sdf-scene`, `runtime-foundation`, `resolver-probe`, `diagnostics-schema` | The matching driver: `--lock-driver`, `--wire-driver`, `--usd-values-driver`, `--wire-scene-driver`, `--scene-journal-driver`, `--sdf-driver`, `--runtime-driver`, `--resolver-driver`; `diagnostics-schema` takes `--runtime-driver` and `--diagnostic-python` |
| Reference service | `reference-service`, `native-reference`, `scene-reference`, `resolver-reference`, `plugin-reference`, `python-reference`, `writer-fuzz` | `--reference-python` and `--reference-openssl` for all; `native-reference` adds `--unary-driver`, `scene-reference` adds `--scene-transport-driver`, `resolver-reference` adds `--resolver-runtime-driver`, `plugin-reference` adds `--plugin-driver`, `python-reference` adds `--python-extension`, `writer-fuzz` adds `--plugin-driver` and `--scene-transport-driver` |
| Kit | `kit-reference` | The reference inputs plus `--kit-executable`, `--kit-package`, `--kit-client-extension` and `--kit-resolver-extension`; optionally `--kit-core-extension` and `--kit-library-dir`; `--kit-release-package` for a released packman package |

`--help` describes every input; `tools/live/ci.py --config <worker config> --output <fresh dir> --seed 42 --dry-run` prints the complete command a CI profile runs. `--writer-fuzz-profile` selects the `ci`, `nightly` or `soak` writer campaign, and `--writer-plan` replays a retained root-field writer plan through `plugin-reference`. `--list` also prints reserved names for future product suites; selecting one is an error, never a pass.

`--seed` sets the master seed; without it the runner draws and records a random one. `--timeout-ms` sets the per-suite failure watchdog (default 60 seconds, longer for `writer-fuzz` and `kit-reference`), and `--max-output-bytes` caps each child log (default 1 MiB). These are harness limits, not product performance budgets.

Each run creates a `run-*` directory under `--artifact-dir` (default `../.cache/live-tests`) holding `manifest.json` (source fingerprint, identities, seeds, outcomes), `junit.xml`, bounded logs and `replay.json`. The runner keeps the 20 newest earlier runs and deletes older ones; `--keep-runs N` (minimum 2) changes that count, and the manifest lists pruned names. `--replay` re-runs the recorded suites, seed and inputs and refuses to run when the source fingerprint or any input identity differs. The exit status is 0 for a pass, 1 for a test failure, 2 for an infrastructure error such as a missing or stale input or a failed service start, and 130 for an interrupt; an infrastructure error is never a product result.

Repository shape checks are `python3 -B ../shared/check_repository.py`, `python3 -B tools/release/check_client.py` and `git diff --check`; they verify paths, links and Markdown, not runtime behavior. Both checks report a file that is not valid UTF-8 with the offset of its first invalid byte, and their text rules skip a file Git classifies as binary, one with a NUL byte among its first 8000 bytes. Do not edit native sources while a compiler runs: the object can hold older bytes with a newer timestamp, so force recompilation of affected inputs.

### Selecting suites and cases

[`tests/contracts/suites.json`](../tests/contracts/suites.json) catalogs every suite, implemented and planned: its product package, its tags, the fixture paths it consumes, the contracts of the [contract catalog](#coverage) it covers, its resource budget and the redaction its logs receive. Instead of `--suite`, `--tag` and `--package` each take a comma-separated list and select every implemented suite that carries one of the tags and belongs to one of the packages; planned suites are selected only by name. The tags are `pr` (the pull-request workflow), `sdk-free`, `native`, `reference` (the reference-service lanes), `campaign`, `manual` (`kit-reference`), `mandatory` (the CI profiles' mandatory suites) and `planned`; the packages are `harness`, `runtime`, `wire`, `scene`, `resolver`, `plugin`, `python`, `kit` and `reference`.

```sh
./tools/live/test.sh --tag pr --seed 42 \
  --uri-library ../.cache/components/liblive_uri_contract_probe.so \
  --wire-driver ../.cache/components/live_wire_envelope_test \
  --lock-driver ../.cache/components/live_lock_noalloc_test
./tools/live/test.sh --suite foundation --seed 42 --scenario test_runner,test_selection.CaseSelectionTests
./tools/live/test.sh --suite foundation --seed 42 --shard 0/4
./tools/live/test.sh --suite native-reference --seed 42 --driver-mode actor-auth-timeout \
  --reference-python ../.cache/live-reference-venv/bin/python --reference-openssl <path to openssl 3.5.9> \
  --unary-driver <build>/live_unary_driver
```

`--scenario` takes case IDs or dotted prefixes (a module, class or method), and `--shard I/N` runs the cases whose ID hashes to shard `I` of `N`, so the shards of one inventory partition it whatever the discovery order. Both apply to the suites that select cases, `foundation` and every reference lane except `kit-reference`; any other selected suite, a scenario that matches no case or a selection that keeps none is an error, never an empty pass. `--driver-mode` runs one diagnostic native driver mode as the only `native-reference` case against a fresh reference service; the catalog lists the modes, which no correctness test runs. The manifest records the selection and `--replay` repeats it.

### Fingerprints, budgets and redaction

Each result in `manifest.json` records a `fixture_fingerprint`, a SHA-256 over the path and bytes of every file of the suite's catalog fixtures, and a `scenario_fingerprint`: over the case IDs the suite recorded, or, for a planned suite, over the ID and requirement text of each contract the catalog assigns it; it is null for an implemented suite that records no cases. `replay.json` keeps the fixture fingerprints, and `--replay` refuses a suite whose fixtures differ. `--list` prints each suite's package, tags and fingerprints.

A suite's `budget` bounds the bytes and files it adds to the run directory; a passing suite over either bound fails, and `resource_usage` records both. A suite's `redact` names patterns of the catalog's `redaction` table, which the runner replaces with `[redacted]` in the suite's log after it ends, keeping a prefix such as `Bearer `; `redactions` counts them. The reference lanes redact bearer tokens and PEM private keys, the credentials their fixtures create. These are harness limits and fixture policy, not product budgets or a real-service redaction policy.

### Service readiness and cleanup

A reference lane's workload reports readiness once a reference service it starts has answered a `Ping` through a real channel; the runner waits for that record under a 120-second failure-only watchdog. A workload that exits before it, reports a failed start or does not report in time has the outcome `service_start_failed`, with the reason, and never reaches its tests' evidence checks.

Each suite runs with a fresh `live-scratch-*` directory as its `TMPDIR`, `TMP`, `TEMP` and `LIVE_TEST_SCRATCH_DIR`. On Linux a subreaper guard owns its descendants; on Windows a Job Object contains the suite and every descendant before they run, with unhandled exceptions fatal rather than waiting on an error dialog. These guards end every descendant, including detached sessions, and remove the scratch directory when the suite ends, times out or is interrupted, or when the runner dies. On Windows, suites run in Python UTF-8 mode. macOS runs each workload in its own process group, signals that group on completion, timeout or interruption, drains output and removes scratch space. Descendants must remain in that group; cleanup after forced runner death and detached descendants is unqualified. Run manifests record `process_cleanup` as `process-group` or `descendant-tree`. Watchdog stack requests are Linux-only.

The macOS foundation inventory excludes exactly the following four cases from discovery before scenario/shard selection. `foundation.json` and the suite result record each excluded ID and reason. Exclusion names must exist in the discovered inventory; unexpected skips and expected failures still fail the selected suite. Linux and Windows run these cases.

- `test_foundation.SupervisorTests.test_successful_parent_reaps_detached_session`: cleanup after a successful workload leaves a detached child.
- `test_foundation.SupervisorTests.test_outer_timeout_reaps_nested_supervised_process`: cleanup of a nested supervisor in another session.
- `test_supervision.RunnerDeathTests.test_an_interrupted_runner_leaves_no_process_or_directory`: cleanup of a detached grandchild after interruption.
- `test_supervision.RunnerDeathTests.test_a_crashed_runner_leaves_no_process_or_directory`: cleanup of a detached grandchild after forced runner death.

## Local setup

The `foundation` suite needs no SDK and runs on Python 3.10 or later; CI runs it on Python 3.12, which the runtime and the Python package require.

**SDK-free component build.** The `uri`, `wire-envelope` and `lock-noalloc` suites need only CMake and a C++17 compiler. This is the component build the pull-request workflow runs:

```sh
cmake -S . -B ../.cache/components -DCMAKE_BUILD_TYPE=Debug -DLIVE_BUILD_WIRE=ON
cmake --build ../.cache/components --parallel 2
./tools/live/test.sh --suite uri,wire-envelope,lock-noalloc --seed 42 \
  --uri-library ../.cache/components/liblive_uri_contract_probe.so \
  --wire-driver ../.cache/components/live_wire_envelope_test \
  --lock-driver ../.cache/components/live_lock_noalloc_test
../.cache/components/live_uri_sanitize 42
```

`live_uri_sanitize` checks the native URI bounds with the given seed. The workflow also builds the same components with `-DLIVE_ENABLE_SANITIZERS=ON` in a separate job and runs `wire-envelope` and `lock-noalloc` under ASan and UBSan.

**Reference interpreter.** The reference-service suites take a Python 3.12 interpreter with grpcio and grpcio-tools 1.78.0 and protobuf 6.33.6, and an OpenSSL 3.5.9 executable; `tools/live/reference.py --identity` rejects other versions, the reference-service tests use Python 3.11 features and the `python-reference` suite imports the package's CPython 3.12 extension. `tools/live/provision.py` creates this environment from the pinned `manylinux_2_35` tool Python of `deps/live-tools.packman.xml`, which also has the Linux pidfd support the test process guard requires; by hand:

```sh
python3.12 -B -m venv ../.cache/live-reference-venv
../.cache/live-reference-venv/bin/python -B -m pip install grpcio==1.78.0 grpcio-tools==1.78.0 protobuf==6.33.6
```

Pass `--reference-python ../.cache/live-reference-venv/bin/python` and `--reference-openssl <path to the openssl 3.5.9 executable>`. The `diagnostics-schema` suite's `--diagnostic-python` is a separate interpreter; the [snapshot schema](ovlive-diagnostic-schema.md#validating-a-snapshot) gives its recipe.

**Formatter.** The C++ format check expects clang-format 18.1.1, which `pip install clang-format==18.1.1` provides, as the pull-request workflow does. `python3 -B tools/release/check_format.py` runs the `clang-format` on `PATH`, or the executable `--clang-format` names.

## Test layers

A component pass is never reported as end-to-end coverage.

| Layer | Suites and checks | What it proves |
| --- | --- | --- |
| Pure Python harness | `foundation` (`tests/harness`), `uri` | The runner, reference models, codecs, reducers, repository rules and documentation pins; no SDK or service |
| Native component drivers | The native component suites above | Each component's invariants against stock-USD or model oracles, allocation faults and diagnostics output; no transport |
| Reference-service lanes | The reference-service suites above | Real gRPC over loopback: status mapping, TLS, fault recovery, reconnect and backend rotation, retained intent after lost replies, many-writer convergence |
| Plugin and package lanes | CTests `live_plugin_package`, `live_python_package`, `live_installed_package`; the install and inventory checks of `tools/live/ci.py` | The installed package loads in both orders, one runtime serves the C ABI, USD and Python, the native samples start from the install prefix, and inventory and notices are exact |
| Kit lane (manual-only) | `kit-reference` | One or two headless Kit processes attach live layers through `UsdContext`, author with plain USD, converge, survive backend rotation and retain edits after a lost reply |

The Kit lane is run by hand, because it needs a provisioned Kit and the unpublished companion extensions. It runs five tests under the `headless-overlay-reference-v2` profile and records the Kit build, selected inputs and startup runtime identity, so `--replay` rejects a different Kit. It qualifies either a build-tree package, bound to the checkout by its identity sidecars, or, with `--kit-release-package`, a released packman package verified from its zip checksum and release manifest; the inputs select the lane explicitly, and the evidence records the lane and the zip's SHA-256 ([Kit guide](ovlive-kit.md#validating-a-released-package)). The [Kit guide](ovlive-kit.md#running-the-kit-reference-lane) describes it from the Kit side.

## The reference service

`tests/reference_service/service.py` implements all ten LiveService RPCs independently of the client, sharing only the generated wire types. Test controls are Python objects, never an RPC or a listener in the plugin. Each case owns fresh state, ephemeral loopback listeners and a seed; synthetic principals set identity, permissions, token rotation and server-side expiry, which the service checks when each RPC starts, as the real service does; a rejection carries no message. An explicitly expired token stays expired whatever the wall clock reads, and only a deadline issued with a token compares against the clock, so a clock step cannot revive an expired token. An append-only ledger records every accepted create, update and delete with resource, incarnation, sequence, bytes and writer, so the ledger alone answers whether a mutation executed, and how often.

- **Named faults.** A fault plan targets an RPC method, attempt and boundary (`before_auth`, `before`, `after_commit` or `before_reply`) with a status failure or a pause gate, which proves whether a request committed before its reply was lost. Every planned fault must fire exactly once; an unused fault fails the case. `plan_unknown` loses one reply and fails the client's operation-ID re-send of it before the service evaluates it, which leaves the write's outcome unknown.
- **Operation IDs.** `UpdateLayer` and `CreateLayer` match a re-send by operation ID as the [design](ovlive-design.md#the-single-operation-id-re-send) describes: a request that applies its write replies `OPERATION_OUTCOME_APPLIED`, the same ID and content after a commit returns that commit's reply with `OPERATION_OUTCOME_ALREADY_COMMITTED` and records nothing, other content is `ALREADY_EXISTS`, and the identity and incarnation checks run first. Records are keyed as the service keys them: an update by session, layer, object and `client_id`, replaced by that writer's next write to the object, and a create by session and operation ID, kept through a replace or delete. An identified unchained update reads its writer's record as its start record once the whole call has been received, and a commit step that finds the record moved since, by the writer's next write or a `restore_checkpoint`, applies nothing and fails `UNAVAILABLE` without `ErrorInfo`, with the service's message starting "this attempt applied nothing, but an earlier attempt of this call may have committed" (`OVERTAKEN` in `operation_log`); the match of the call's own operation comes first. A chained update relies on its predecessor check instead. The `stale` write fault returns plain `UNAVAILABLE` while retaining the first attempt's commit work behind a release gate, and `stale_start` retains it before its start-record read; these faults exercise late-write ordering while the channel stays usable, independently of TCP reconnection availability. A `stale_start` released with a status drops its retained work before that read. The `delay_start` write fault holds a call before that read, as a handler waiting at upload admission with its body received does, and with a status set before its release fails the call with it, as the service drops a call still waiting at its deadline. Content is the SHA-256 over the layer name, a 0x00 byte and the concatenated payload, whatever the chunking. `operation_log` records each match. Setting `operation_ids` to false models a server older than operation IDs, which ignores them, applies every request and replies `OPERATION_OUTCOME_UNSPECIFIED`. `Ping` reports `operation_ids` and `chained_writes`: `advertise_capabilities` false reports neither, so the client neither chains nor re-sends, `chained_writes` false models a service with operation IDs but without chaining, and `pre_chaining` models a replica that refuses the chained header `INVALID_ARGUMENT` before reading any chunk while the `Ping` still reports chaining; a chained call whose operation ID is in `pre_chaining_operations` reaches such a replica once. A chained call waits for its predecessor after reading its content until it commits, its deadline or a cancellation, which drops it with nothing applied (`dropped` in `chain_log`); with `no_wait`, and in a stale commit step that runs after its call was answered, it is refused at once. A refusal's `last_record` is `absent` before any write and after `restore_checkpoint`, `operation` while the writer's record holds an operation ID and `no_operation_id` after a write without one, and the empty predecessor matches only `absent`. Every `INVALID_ARGUMENT` the service gives a recognized chained call carries an `INVALID_UPDATE` `ErrorInfo`. `arrival_log` records each identified update header with whether it is chained and `no_wait`, its monotonic arrival time and its cutoff, the time ahead of the call's deadline, by half the remaining time and at most 0.5 s, after which a waiting call is refused instead of committed, so the client receives the refusal before its deadline. The scene drivers report ready only once a `Ping` has reported their endpoint's capabilities, so whether a case's writes chain and re-send never races it.
- **Client keepalive.** `keepalive_interval_ms` (default `None`, a service without the client keepalive, which returns no interval and refuses a `JoinSessionKeepalive` frame `INVALID_ARGUMENT`) sets the interval returned to a join that sets `client_keepalive`. Such a join that receives nothing for three intervals ends `UNAVAILABLE` with the service's `google.rpc.ErrorInfo` reason `CLIENT_KEEPALIVE_TIMEOUT`, and its peers receive one `PeerLeft`. The keepalive clock moves only through `advance_keepalive_clock`, which ends every join that is due and returns their connection IDs, so a timeout happens exactly when a test advances it. Each request frame read restarts a join's timer; the service restarts it on any bytes of the stream, which the Python gRPC server does not expose below whole frames. `joins`, `keepalives` and `keepalive_timeouts` record each join's opt-in and interval, the keepalives each connection sent and the joins that timed out.
- **Second backend.** A second service instance shares the authoritative state, so a test can rotate a client to another backend under the same authority and check resume from a nonzero cursor.
- **HTTP/2 proxy.** `http2_proxy.py` forwards frames byte for byte and injects faults that an application-level status cannot reproduce: real stream resets, a graceful `GOAWAY`, and an ingress rejection of the next new streams, which it answers before the service with an HTTP 401 or a trailers-only `grpc-status` 16, as an authenticating ingress does. The rejected header block still reaches the service, so a rejected client-streaming request such as `UpdateLayer` can start there and count an attempt before the proxy cancels it, whereas Envoy ext_authz forwards nothing; a rejected unary request never starts. It can terminate TLS with a per-case test certificate authority in front of plaintext backends, as the deployed ingress topology does, and `RotatingProxy` can too. It records frame metadata, never header or payload contents.
- **Scene profiles.** The base service treats layer content as opaque; `graph_service.py` adds the independent graph model, commits whole updates under the [service conflict rules](ovlive-design.md#service-conflict-rules) and generates snapshots and resume diffs. Before it processes an `UpdateLayer` or `CreateLayer` upload it counts the delta's entries as the service does and refuses one over its entry limits `INVALID_ARGUMENT` with the service's `google.rpc.ErrorInfo` (`DELTA_TOO_LARGE` or `CHILDREN_LIST_TOO_LONG`); `delta_entry_limit` and `children_list_limit` default to the service's 99,999 and 100,000, and a case lowers them below the profile's own record bound to reach the refusal. `refuse_updates` and `refuse_creates` plan UNAVAILABLE refusals of the next `UpdateLayer` or `CreateLayer` uploads that read each whole upload and apply nothing, with or without the service's `ErrorInfo` and a `google.rpc.RetryInfo` delay, and record each refused upload's operation ID, writer and payload digest; `creates` records every `CreateLayer` upload's operation ID, payload digest and arrival time.

The `reference-service` suite runs the service's self-tests. `--reference-python` and `--reference-openssl` are the interpreter and OpenSSL 3.5.9 executable that [local setup](#local-setup) describes; TLS fixtures use that OpenSSL to generate a test certificate authority and server certificates. It models no deployed authorization or durability policy; its fidelity limits are on the [support boundary](ovlive-support-boundary.md#supported-configuration).

## Oracles

No test derives its expected result from the code under test.

- **Graph model.** `tests/reference_service/scene_graph_wire.py` and `scene_graph_model.py` implement a bounded profile of all eleven spec types, the six structural commands, typed fields and time samples. Its value families are bool, int32, finite double, token, specifier, variability, token and path vectors, path list operations and the families Kit's presence layer authors: string and string array, token array, float, double array, and matrix4d, vec2f, vec3d and vec4f with their scalar and array forms. Floating-point families are held and compared by their exact IEEE-754 bits, so a sign-only or NaN-payload change is a change. Every other family, including a string that is not UTF-8 or holds NUL and a nonfinite scalar double, is rejected as `unsupported`, a profile boundary rather than evidence of malformed wire; truncation, trailing bytes, partial array elements and over-limit strings or arrays are rejected as `malformed` or `limit`. `live_scene_graph_probe` applies the same bytes to the production `WireScene` builder, and `tests/native/scene/graph_reference.py` compares the outcome and entire state after every attempt.
- **Many-writer campaigns.** `writer-fuzz` runs seeded multiprocess campaigns (`ci`: 2 and 8 root writers, 4 graph writers; `nightly`: up to 32 root writers and 8 graph writers) against a fresh service per case. `nightly` also runs one `long-rotations` case: 4 plugin writers with the production retry options through 500 event-driven rotations between two shared-state backends, each writer queuing one edit per outage, with every writer reconnecting once at the first backoff step and all writers converging after each rotation. Every service commit must match exactly one admitted edit or planned peer effect, every admitted edit must end reflected, superseded, rejected or retained for recovery, and all clients and a fresh observer must agree on complete typed scenes. The `soak` campaign runs one case: 4 plugin writers through 600 rotations with a 5-second READY pause between them, proactive token refresh on a 180-second lifetime, a server-side expiry every 100 rotations and a hold for a periodic `Ping` in one READY window every 100 rotations; its duration is the product of the count and the pause, the pause is load and never synchronization, and it asserts exact counts, logical gauges, threads and open files back to their warm-up values, gRPC's iomgr timer threads (`grpc_global_tim`), which gRPC only adds and keeps until shutdown, at most `SOAK_MAX_GRPC_TIMER_THREADS` apart from the other threads, and stated anonymous-RSS growth, slope and peak-RSS tolerances.
- **Reducer.** On a mismatch, `graph_reduction.py` keeps the original evidence and shrinks the failing prefix by deleting batches, commands, fields and sample records. Each trial is a fresh process; only the same first discrepancy at the same original edit may replace the candidate, and a crash or watchdog expiry never does. `reduction/reduction.json` names the payloads; `deletion_minimal` is true only after a complete fixed-point pass.
- **Replay.** A replay checks source, native, SDK and interpreter identity and every payload hash before it launches; a reproduced defect exits 1 and a valid replay that does not reproduce exits 2.

With a configured native build and matching SDK environment:

```sh
cmake --build "$BUILD" --target live_scene_graph_probe
ctest --test-dir "$BUILD" -R '^live_scene_graph_(reference|reduction)$' --output-on-failure
python3 -B tests/native/scene/graph_reference.py --probe "$BUILD/live_scene_graph_probe" --artifact-root "$BUILD/graph-reference-artifacts" --seed 42
# Reproduce a recorded failure; a matching defect exits nonzero.
python3 -B tests/native/scene/graph_reference.py --probe "$BUILD/live_scene_graph_probe" --artifact-root "$BUILD/graph-replay-artifacts" --replay-reduction "$FAILURE/reduction/reduction.json"
```

Each `graph-*` artifact directory holds `seeds.json`, the exact `.ompf` inputs, expected records in `cases.json`, identities and process results in `evidence.json` and `native.log`; a disagreement adds `mismatch.json`. `--reduction-trials` sets the reduction budget (2 to 256, default 48).

## Determinism rules

These rules apply to every correctness test.

- **Barriers, not sleeps.** Establish the state under test with fake clocks, controllable schedulers, events, barriers or service pause gates, never with a sleep, elapsed time or timeout expiry. A healthy test finishes as soon as its assertions can run. When a dependency's timing cannot be controlled, add an observable event or test seam.
- **Failure-only watchdogs.** Real-time timeouts only catch hangs; no passing path waits for one. Real clocks belong only in performance measurements.
- **Seeds before workers.** Record the master seed, per-writer derived seeds and the generated operation plan before any worker starts, so a crash cannot hide its seed. A seed reproduces generated inputs and scheduler choices, not OS thread scheduling.
- **No retry into a pass.** A failed run keeps its evidence; a diagnostic rerun is a new run with its own seed and artifacts.

When a runner watchdog expires on Linux, the runner asks every descendant process that installed a stack-dump handler for its thread stacks, waits at most 3 seconds, then kills the tree; Windows has no signal to request stacks with, so there the runner kills the tree without dumps; the outcome stays `timeout`. Native test drivers install the handler, and Python test entry points register `faulthandler`, only when `LIVE_STACK_DUMP_PREFIX` is set, which the runner sets per suite and per CI step. Dumps are `<index>.stacks.<pid>` beside the suite log (`<step>.stacks.<pid>` for a CI step) and every non-empty dump is listed as `stack_dumps` in `manifest.json` and the CI summary whatever the outcome, including one a driver's in-process watchdog writes before it aborts; a run removes dumps an earlier run left at its prefix. A native dump lists each thread's frames between `live-stack-thread` and a final `live-stack-dump end` line whose `missing` counts threads that did not answer, including ThreadSanitizer's own runtime thread; frames of a driver without exported symbols print as offsets, which `addr2line -f -C -e <driver> <offset>` resolves. Python processes show Python frames only.

A build-path change needs plugin loading, native sample and Python import checks from outside the source tree. Credentials, GPU and deployed-service access are never ordinary CI inputs. Report an unavailable local capability; never skip it into a pass.

A passing path waits out a real deadline only when that deadline's expiry is the behavior under test and the outcome is classified deterministically before the wait can matter: either credential starvation is recorded before a 1 ms deadline, the minimum the API accepts (`actor-auth-wait-open-deadline`, `public-deadline-starved`, `join-auth-deadline`, `--discovery-auth-deadline` and the resolver authentication deadline), or the completion the deadline bounds cannot arrive because a pause gate, a held host gate, a missing credential or a hung fixture holds it (the client RPC deadline, metadata deadline, read first-response deadline, auth-wait, bounded-wait and runner-watchdog cases). Sleeps and fixed windows are never synchronization: every other real-time bound is a failure-only watchdog, and a polling loop spins only on an observable predicate under one. No correctness test establishes its state by elapsed time; peer departure, actor idleness, layer readiness, the prepared-activation deadline (`--prepared-timeout`, which expires the initial-open deadline through `SceneAttachment::expireActivationForTest` while the bootstrap is held) and a read attempt's first-response deadline (the scene driver's `expire-read`, which expires it through `SceneAttachment::expireReadForTest` while a pause gate holds the response) each have a test seam or a status callback. The `actor-auth-timeout` native driver mode lets a real token expire on purpose; it probes the auth watchdog for the open item `test-intermittent` in the [support boundary](ovlive-support-boundary.md#open-items), and no correctness test runs it.

## Coverage

[`tests/contracts/catalog.json`](../tests/contracts/catalog.json) maps each required behavior to the tests that cover it. Each contract has an `id`, an owning area (from core scene semantics and ABI loading to recovery, thread safety, Kit and packaging), the `requirement`, a `status`, whether it is `release_required`, the `cases` (test files or `file::Class.test` names) and a `coverage_limit` stating what the cases do not reach.

`foundation` checks that every case path exists and that each status agrees with its cases. Coverage is counted in contracts and state transitions, not test counts or line coverage. When you add behavior, extend its contract and name the cases; record what they cannot reach in `coverage_limit`.

## Sanitizers

The `asan` profile of `tools/live/ci.py` builds every native lane with AddressSanitizer and UndefinedBehaviorSanitizer (`LIVE_SANITIZER=address`) and runs them with leak detection on. `tools/live/sanitizer.py` owns the runtime recipe: `detect_leaks=1`, full unwinding on allocation (the USD SDK has no frame pointers) and `halt_on_error=1`. The `tsan` profile builds the same lanes with ThreadSanitizer (`LIVE_SANITIZER=thread`; `LIVE_ENABLE_SANITIZERS=ON` is an alias for `LIVE_SANITIZER=address`) and runs them under `setarch <machine> -R`, where `<machine>` is the host's `x86_64` or `aarch64`; every report is logged per process under the run directory with `halt_on_error=0`, the process still exits nonzero, and the runner fails any suite that leaves a report file. Suite reports are `<run>/<index>.tsan.<pid>` and step-level reports are `<output>/tsan.<pid>`; each suite's `sanitizer_reports` in `manifest.json` lists its files, and `halt_on_error=0` with exit code 66 makes the run red.

`tools/live/lsan.supp` and `tools/live/tsan.supp` follow fixed rules, which `tests/harness/test_sanitizer.py` enforces:

- LeakSanitizer entries name third-party USD or TBB allocating frames, or statically linked OpenSSL frames by function or source file, only; never libstdc++ or allocator frames.
- Each `race:`, `called_from_lib:`, `mutex:` or `deadlock:` entry names a third-party frame: prebuilt USD and TBB, statically linked gRPC, absl, upb and OpenSSL, the glibc dynamic loader, or a third-party header template inlined into our code; an entry never names a product frame.
- Each entry follows a comment giving its owner and reason.
- A path-keyed entry names a third-party source tree (OpenSSL's `/src/crypto/`, `/src/ssl/` or `/src/providers/`, USD's `/pxr/`, gRPC's `/src/core/`, glibc's `/nptl/` or `/sysdeps/`), never a product or test tree; an entry anchored at both ends (`^name$`) names one bare third-party C symbol, never a namespaced, templated or mangled C++ name or a product C API name.
- A leak whose allocation site is `omni::usd::live` or a `live_*` binary is a product or test defect to fix, never a suppression.
- A ThreadSanitizer report whose happens-before edge runs through uninstrumented third-party code (a handoff or a lock inside a prebuilt library) may be keyed on that third-party frame only; a report with both accesses in product code and no third-party edge is a product or test defect to fix or annotate, never a suppression.

USD's `TfNotice::Register` allocates its deliverer in a header template compiled into our binaries and loses it when the notice registry's own allocation throws. A suppression would have to name the product frame that inlines it, so the product's one registration, in `BoundLayer::ensureSetup`, runs inside a LeakSanitizer disabled scope (`__lsan::ScopedDisabler`, address builds only) instead. LeakSanitizer treats allocations in that scope as roots, and the lost deliverer's weak pointers reference the `BoundLayer`, the layer's live state, so the scope also hides a product leak of that state and everything it owns on the fault path; the `asan` scene lane's zero-report run of the allocation-fault sweep of the live format's Read, which reaches that path, is what shows the state is freed.

LeakSanitizer matches an entry against every frame of a stack, so each entry also hides leaks that pass through that frame. A ThreadSanitizer `race:` entry matches a function, file or module name in any frame of the racing access stacks (or a global variable's name or module), never a heap allocation stack or a thread creation stack, so each entry also hides a product race whose access stack passes through it; that cost is why both lists stay short. A `race:` or `called_from_lib:` entry that names a module names exactly one library.

No `race:` entry names a USD module. The USD-linked test executables (`live_scene_transport_driver`, `live_wire_scene_test`) keep the standard allocator under ThreadSanitizer, so USD calls it directly and `called_from_lib` ignores its allocations; their allocation-fault cases run only in the other profiles. The remaining USD entries key on USD 25.11 header templates compiled into our binaries (`VtValue`, `TfDelegatedCountPtr` and its count hooks, `TfToken`, `TfPointerAndBits`, `VtDictionary` and the `TfRefPtr` counters), anchored with `^` at the start of the frame's function name so that none matches a product function that only takes or returns a USD type. Each hides a race whose access runs inside that template, including one reached from product code: `HostSceneStorage::_VisitSpecs`, `WireSceneBuilder::build`, `buildSceneCandidate`, the layer actor's and scene journal's value handling, and wire value decoding. Two USD entries key on other third-party frames: the `PcpLayerStack` frame in `libusd_pcp`, whose constructor and destructor call the `std::shared_ptr` count templates our executables export, and libstdc++'s out-of-line `std::string::find`, which uninstrumented USD code calls on TBB workers on strings a host thread built; the second also hides any other race whose racing read is that libstdc++ function. The gRPC entries never match the `grpc_schema_probe.cpp` test file, the `live_grpc_schema_probe` module or a product function that only takes a gRPC C++ type: C symbols and the C++ API are anchored at the start of the function name, gRPC C types match only inside a parameter list, and the C++ API otherwise matches only as a template argument or in `grpc::internal`. gRPC's TLS teardown functions `ssl_protector_destroy` and `secure_endpoint_unref`, which free the frame protector and the secure endpoint on an event-engine thread after gRPC's uninstrumented last unref, are anchored at the start and closed by their parameter list's opening parenthesis, so each names that one function. Those two entries rest on the racing addresses, which lie inside gRPC's frame-protector and secure-endpoint objects, because ThreadSanitizer does not restore the previous-write stacks of those races. Product code that hands an object to uninstrumented code annotates the handoff instead: the completion-queue tags (`submitTag`, whose release is the last access before completion) and a `HostSceneProjection`'s publication to USD. The `tsan` profile refuses the `kit-25.11` USD profile, whose libraries and namespace these entries do not name.

## Qualification gates

Seven gates decide whether a build is releasable; the [support boundary](ovlive-support-boundary.md#qualification-boundary) records each gate's status and open work.

| Gate | What the lanes prove |
| --- | --- |
| Data preservation and many-writer fuzzing | `writer-fuzz`, `plugin-reference`, `scene-reference` and `python-reference` show that seeded many-writer histories account for every admitted edit against the service ledger, that accepted and ambiguous intent survives failure, and that no issued mutation is reissued automatically |
| Concurrency, deadlocks and memory safety | The `asan` profile runs every native lane under ASan, UBSan and leak detection, and the `tsan` profile under ThreadSanitizer with the owned third-party suppressions in `tools/live/tsan.supp`; `lock-noalloc` proves allocation-fault safety of nested lock ownership |
| Performance | The [storage benchmarks](ovlive-benchmarks.md) characterize storage cases and compare two revisions, and the [interactive edit benchmark](#interactive-edit-benchmark) compares edit-to-peer latency, publish throughput and backlog with the omni.client live layer path; frozen per-case budgets belong to this gate |
| Error handling and reconnect recovery | `native-reference`, `scene-reference`, `plugin-reference` and `resolver-reference` cover rejection before execution, reply loss after commit, stream resets and `GOAWAY` through the HTTP/2 proxy, backend rotation, token refresh, server-side token expiry and ingress rejection, TLS through the HTTP/2 proxy and shutdown, reconnect catch-up aggregates that retire the layer's own acknowledged writes and a live aggregate delivered before an own write's reply, which absorbs it (`scene-reference`) and a read paused at its high-water mark while the layer closes or fails or the service ends the stream (`native-reference`); the nightly `long-rotations` writer case qualifies rotation by count, 500 event-driven backend rotations per layer, and the `soak` profile by one 60-minute soak on one worker |
| Kit integration | `kit-reference` proves attachment, plain-USD authoring, convergence, rotation and retained edits in headless Kit |
| Packaging | The package CTests and the install, notice and exact-inventory checks prove relocated loading and complete notices on both USD profiles, and `tools/release/archive.py` creates the release archive reproducibly from one stage and verifies it member by member |
| Observability | `diagnostics-schema` validates native snapshots and malformed consumer fixtures against the [snapshot schema](ovlive-diagnostic-schema.md), and the native checks compare emitted events with the [event catalog](ovlive-diagnostic-catalog.md); emitter coverage, overhead and memory budgets belong to this gate |

One gate never stands in for another: a sanitizer-clean run does not prove correct scenes, and convergence does not prove preservation, because every client can lose the same edit.

The [qualification campaign](ovlive-ci.md#qualification-campaign) lists the runs a release candidate completes, in order, and how to record them before these gates are claimed.

## Interactive edit benchmark

`tools/live/edit_benchmark.py` measures sustained interactive editing against the omni.client live layer path: the time from a host edit to its visibility at a peer, the turns per second a writer publishes, and its backlog. It is a characterization, never a CI or presubmit gate, and it asserts nothing; it writes `results.json` and `summary.md`, whose last table compares ovlive with the baseline measurement by measurement. Results belong on pull requests, not in this guide.

**Acceptance bar.** ovlive at least matches Omniverse Client Library 2.74.0 driven as the pipelined baseline, one coalesced update per frame with at most 16 in flight as omni-spectree's default live layer format drives it, with its USD host cost (the `client-library` writer below), at 20, 50 and 100 ms of added round trip with the Kit-frame ovlive writer described below. For the sustained `single` and `multi` scenarios the bar is edit-to-peer latency (p50 and p99) and published throughput. For the `burst`, `multi-burst` and `batch-in-one-frame` scenarios it is edit-to-peer latency (p50 and p99) only, because the Kit-frame writer runs a flush round trip every frame, which caps burst throughput by construction, so burst throughput compares unlike things. Every scenario also requires complete delivery on both sides: the writer accepts every turn it authors, the peer sees every accepted turn, no write fails and the writer drains. Latency covers only the turns a peer saw, so a run that refused or lost its slowest turns would otherwise look faster; an incomplete ovlive run misses the bar, and an incomplete baseline is no bar to meet, so that comparison misses the bar until a rerun delivers every turn. The baseline is 2.74.0 because it is the last release that keeps several `UpdateLayer` calls in flight per object; 2.75.0 and later send one write per object at a time, a weaker baseline.

To re-check the bar, build the ovlive revision under test (`./build.sh` puts its Python extension under `../.cache/local/build`), install the baseline package with `tools/packman/packman install omni_client_library.manylinux_2_35_x86_64 2.74.0`, which prints the directory it installs to, and run the benchmark with the reference-service interpreter, which has `grpcio`, `grpcio-tools` and `protobuf`. `--python-extension` names the build's `_live` module and `--client-library` the package root, the directory that holds `release/bindings-python`:

```sh
<reference python> tools/live/edit_benchmark.py --seed 42 \
  --python-extension ../.cache/local/build/plugin/omni_usd_live/python/omni/usd/live/_live.cpython-312-x86_64-linux-gnu.so \
  --client-library <installed omni_client_library 2.74.0 directory> \
  --scenarios single,multi,burst,multi-burst,batch-in-one-frame --rtt-ms 20,50,100 \
  --label ovlive=<revision> --label baseline=omni_client_library_2.74.0
```

For an ovlive-only orchestration smoke run without the baseline package, use `--clients ovlive --no-client-library-reader --scenarios single --rtt-ms 0 --jitter-ms 0 --duration-s 1`. The extension must come from the build tree with its adjacent SDK identity manifest; an installed module without that manifest is not a benchmark input. This run checks writer, peer, proxy and report generation and makes no baseline comparison.

The bar holds when every row of the summary's comparison table reads `yes` under "Meets the bar", that is, when no cell in the bar carries a `(worse)` or `(incomplete)` mark; the "Turns delivered" column counts the turns each side's peer saw of the turns it authored, and a row that misses the bar through incomplete delivery names the incomplete side. p95, backlog and burst throughput cells carry an `(info)` mark and never decide it. A row whose baseline writer reports a client library version other than 2.74.0, with any build suffix, reads `no (baseline <version>, not 2.74.0)`; such a run characterizes that version and decides no bar. To check a build outside this checkout, point `--python-extension` at that build's `plugin/omni_usd_live/python/omni/usd/live/_live.cpython-312-x86_64-linux-gnu.so`; the benchmark loads the `omni_usd_live` plugin package that contains it and the USD libraries named by the `.manifest.json` beside it. Before any case runs, the benchmark fails unless the extension, the plugin artifacts and the SDK trees hash as that manifest records; it does not compare sources with the checkout it runs from.

Each case starts fresh processes: a reference service, a TCP proxy in front of it, a raw `SubscribeReadLayer` peer, an Omniverse Client Library peer and one writer, every client connecting through the proxy. The proxy adds half the round trip in each direction plus a uniform per-chunk jitter (`--jitter-ms`, default 2) drawn from generators seeded by `--seed`, and never reorders bytes. The service is the reference `LiveService` relaying each payload verbatim in the Live Edit service's per-commit catch-up mode (`--service opaque`, the default), with the capability queries Omniverse Client Library makes before using a direct endpoint; `--service graph` uses the graph reference service instead, whose per-commit validation costs tens of milliseconds for the multi-prim scene and dominates every client. The layer is created before the writer starts, with prims `/P<i>` holding double attributes `a<j>`; a turn sets every attribute's default to the turn number, which the peers decode to see which turns are visible.

| Scenario | Turns |
| --- | --- |
| `single` | 60 Hz for `--duration-s` (default 10), one attribute per turn |
| `multi` | 60 Hz for `--duration-s`, 50 prims with 3 attributes each per turn |
| `burst` | `--burst-turns` (default 1,000) one-attribute turns back to back |
| `multi-burst` | `--burst-turns` turns of 50 prims with 3 attributes each, back to back |
| `batch-in-one-frame` | `--burst-turns` change blocks of 50 prims with 3 attributes each inside one frame, as a script authoring a large batch does; it reports how many turns each writer accepts |

`--rtt-ms` selects the added round trips (default 20, 50 and 100) and `--clients` the writers. `--rate-hz` changes the sustained rate, so a sweep at `--rtt-ms 0` finds a client's CPU ceiling, and `--scene-prims` grows the layer with prims the turns never edit, which shows how per-update cost depends on layer size; the `client-library` writer's host layer holds the same scene. `--writer-wrapper` runs the writer under a command prefix such as a sampling profiler, with `{dir}` expanding to the case directory. `--service-option NAME=VALUE`, repeatable, sets a reference service state attribute, such as `chained_writes=false` to measure ovlive against a service without chained writes. The benchmark uses the reference service and protocol of the checkout it runs from, so a revision whose protocol differs runs that revision's copy of the benchmark.

- **`ovlive`** drives the ovlive under test through its Python bindings as a USD host. Each turn models a Kit frame: the main thread authors the turn in one `Sdf.ChangeBlock`, then runs host jobs until the flush job that turn requested has been dispatched and run, waiting at most `--frame-wait-ms` (default 2) because the job reaches the host queue from the runtime's thread. A batch runs the jobs once, after its last turn. A USD call the layer refuses, such as one past the host edit buffer quota, is recorded as a refused turn and the run continues.
- **`client-library`** models omni-spectree's default live layer format on the real Omniverse Client Library, host cost included. The host authors each turn into an in-memory `Sdf` layer with the same USD calls and change block as the ovlive writer, a change-notice listener and the writer record which specs changed, and each tick builds the delta from those specs' current values in the layer and encodes it. Edits since the last tick coalesce into one update, sent at the tick only while fewer than 16 updates are unacknowledged (`PENDING_UPDATES_STOP_COUNT`), and otherwise kept buffered. A sustained scenario ticks at 60 Hz, a burst once per turn and a batch once after its last turn. It authors with the USD SDK of the ovlive build that `--python-extension` names, and it encodes with the reference graph profile's Python encoder, which costs more per field than omni-spectree's native encoder.
- **`client-library-record`** is the same write pattern without host USD work: each turn only records its values, so its authoring rate is far above any USD host's. It is kept for continuity with earlier results and is outside the acceptance bar. Client library 2.74.0 keeps several `UpdateLayer` calls in flight per layer; 2.75.0 and later send one at a time.

A turn's latency runs from the moment the writer authors it to the first update at the peer that holds it or a later turn, and, with the opaque service, splits at that update's commit into edit-to-commit and commit-to-peer times; the graph service records no commit times, so its cases have no split. Readers record arrival times and decode after the read ends, so decoding never delays an arrival. The raw reader gives the primary latencies; the Omniverse Client Library reader applies that library's default jitter reduction, calling `omni.client.live_process` every millisecond, and gives the secondary column. Published turns per second is the turn count over the time from the first edit to the last turn's visibility, the backlog is the most turns authored and not yet visible at any edit, and turns per update shows coalescing. The writer peak reports ovlive's `pending_write_count`, `buffered_edit_count` and turns spent `BLOCKED`, with the snapshot's `layer_writes` window metrics when the build reports them, or the baseline's updates in flight and buffered turns; an ovlive writer's results also keep its diagnostic metrics and most recent records.

Each run writes `results.json`, `summary.md` and one directory per case with the raw timelines, `metrics.json` and the process logs under `--output` (default `../.cache/edit-benchmark/run-*`). `results.json` records what it measured under `identities`: the ovlive extension path with the full SDK identity manifest beside it, which also names the USD libraries the `client-library` writer authors with, and the Omniverse Client Library package path with the version and build string it reports; the run fails after writing its results if a baseline writer reports another version. Each case's metrics carry a `delivery` record of authored, visible and refused turns, failed writes, drain and whether the drain timed out, where an ovlive layer that fails counts the write that failed it, and each comparison carries both sides' records and the incomplete sides. Times are wall-clock measurements of real processes on one host, so repeated runs vary; seeds fix the workload and the proxy jitter, not the timings. The baseline is a model of omni-spectree's write pattern on the real library, not omni-spectree itself: it encodes the same graph wire profile as the reference service, never reads its own layer and settles an update when its callback arrives.

## Manual and deployed validation

The [support boundary](ovlive-support-boundary.md#supported-configuration) states the policy for service-backed testing. Two kinds of validation happen outside this repository's automation:

- **Manual Kit validation.** In a running Kit with the package and companion extensions installed, check: session list, create, join and leave; presence and merge messages; opaque URIs with no channel assumptions; credential rotation during edits; the per-layer error state and authoring and merge gating with diagnostics disabled; exporting a failed layer and reopening it; closing and reopening stages; and offline shutdown. Record the Kit build, package and results separately from automated results. The outstanding manual Kit rerun is an [open item](ovlive-support-boundary.md#open-items).
- **Service-owned end-to-end tests.** The service's own end-to-end suite consumes the package against deployed backends. Record the plugin, ABI and protocol identity with each external result; a reference-service pass does not stand in for it.

## Known test-environment issues

Kit's frame-rate limiter can request multi-second sleeps after the realtime clock jumps relative to the monotonic clock, which stalls a Kit process with pending work; run Kit on a host with a stable realtime clock. The intermittent SIGSEGV at process exit comes from the TBB thread-naming observer in stock `omni.tbb.globalcontrol`, and the companion `omni.usd.core` overlay, selected in the reference lane with `--kit-core-extension`, fixes it.

On Windows the C runtime flushes buffered standard output only in its own process detach, after `ExitProcess` has ended every other thread of the process. A process can end before that flush, with its exit code, when another thread is still exiting at that moment, as gRPC's threads still are for about two milliseconds after the runtime shuts down, or when a library's process detach enters a lock that a terminated thread held; a driver's final record then arrives cut at a multiple of the 4 KiB buffer, or not at all. Every native test driver links `tests/native/support/StackDump.cpp`, which leaves its standard output unbuffered on Windows, and the samples flush each record as they write it. `tests/harness/test_exit_flush.py`, in `foundation`, reproduces such an exit on every pull request's Windows runner and checks both disciplines.

## Allocation and edit-boundary probes

Two opt-in diagnostics reproduce the USD boundaries of [failure containment](ovlive-design.md#failure-containment). Both are outside the default build and CTest, and neither is a safety pass: each report records `product_qualified: false`.

The edit-boundary probe reproduces the known USD limitations beside a successful namespace-move control. Build the explicit target in a configured scene-SDK build and run the supervised driver:

```sh
cmake --build "$BUILD" --target live_usd_edit_boundary_probe
python3 -B tools/live/usd_edit_boundary.py --driver "$BUILD/live_usd_edit_boundary_probe" --artifact-dir ../.cache/usd-edit-boundary
```

Each case runs in a fresh process; the runner validates manifests before and after, identifies the loaded Sdf library, and exits zero when the limitations reproduce. On USD 25.11 and Kit USD `0.25.11.kit.5-gl.21209`, it shows that ignoring a data move leaves `/P` in storage while USD moves a retained handle to a nonexistent `/Q` and returns success, and that a delegate that disables editing still allows the current field write.

`tools/live/usd_allocation.py`, with `--driver` naming the built `live_wire_scene_test` and a required `--artifact-dir`, injects one C++ allocation failure on the calling thread during a complete public USD operation and compares stock SdfData with the live projection under the same seeded layer, stage and retained handles. `--operation` selects namespace move, child creation, field, dictionary or time-sample edits, `--backing` selects `stock` or `projection`, and `--controls-only` runs only the uninjected controls. Each injection index runs in its own child; a crash, truncated output or failed cleanup cannot finish a sweep, and the ten-second bound is a failure-only watchdog. `complete: true` means every sweep reached a clean uninjected success past the observed allocation sites. The campaign covers calling-thread `new`, not every SDK allocator.

The `runtime-foundation` and `scene-reference` lanes sweep every allocation before a live layer's first RPC (actor open, `SdfLayer::New` of the live format, and the `Read` hook up to its bootstrap wait) and require each failure to report `RESOURCE_EXHAUSTED` or propagate the allocation exception, and to leave nothing behind; the probe above shows why no lane can sweep inside a complete USD operation. The `SdfLayer::New` sweep continues under a fresh layer identifier after each throw, because a failure inside USD's own layer constructor leaves a dead layer-registry entry that aborts a later layer of that identifier.
