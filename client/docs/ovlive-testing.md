# Testing guide

This guide explains how ovlive is tested: the test runner and its suites, what each layer proves, the independent reference service and oracles that judge results, the rules every test follows, and the qualification gates the lanes feed. It is for engineers and agents who run tests, add one, or read a failure. The [build guide](ovlive-build.md) builds the binaries the suites consume, the [CI guide](ovlive-ci.md) runs them on a provisioned worker, and the [support boundary](ovlive-support-boundary.md) states what the lanes cover today and what is open.

Commands in this guide run from the repository's `client` directory, and the paths they name are relative to it; build output and evidence go to `../.cache`, the `.cache` directory at the repository root.

## Running the tests

`tools/live/test.sh` runs `tools/live/test.py`, the entry point for every suite, with the interpreter that `LIVE_TEST_PYTHON` names (default `python3`). `tools/live/test.bat` is its Windows counterpart. Linux and Windows use descendant-tree guards; macOS admits only `foundation`, `uri`, `wire-envelope` and `lock-noalloc`, using bounded process-group cleanup and a foundation inventory with four explicit detached-process exclusions. SDK-dependent and reference-service suites require Linux/Windows descendant-tree containment; direct macOS package checks use [macos_ci.py](../tools/live/macos_ci.py). Other platforms run no suite and report an infrastructure error (`platform`). It never downloads a dependency; every binary and interpreter is an explicit input whose build manifest and source identity the runner validates first.

```sh
./tools/live/test.sh --list
./tools/live/test.sh --suite foundation --seed 42
./tools/live/test.sh --replay ../.cache/live-tests/run-EXAMPLE/replay.json
```

`--suite` takes a comma-separated list; the default is `foundation`. The suites are:

| Family | Suites | Required inputs |
| --- | --- | --- |
| Python harness | `foundation`, `uri` | None for `foundation`; `--uri-library` for `uri` |
| Native components | `lock-noalloc`, `wire-envelope`, `usd-values`, `wire-scene`, `scene-journal`, `sdf-scene`, `runtime-foundation`, `resolver-probe`, `diagnostics-schema` | The matching driver: `--lock-driver`, `--wire-driver`, `--usd-values-driver`, `--wire-scene-driver`, `--scene-journal-driver`, `--sdf-driver`, `--runtime-driver`, `--resolver-driver`; `diagnostics-schema` takes `--runtime-driver` and `--diagnostic-python` |
| Reference service | `reference-service`, `native-reference`, `scene-reference`, `resolver-reference`, `plugin-reference`, `python-reference`, `writer-fuzz` | `--reference-python` and `--reference-openssl` for all; `native-reference` adds `--unary-driver`, `scene-reference` adds `--scene-transport-driver`, `resolver-reference` adds `--resolver-runtime-driver`, `plugin-reference` adds `--plugin-driver`, `python-reference` adds `--python-extension`, `writer-fuzz` adds `--plugin-driver` and `--scene-transport-driver`, and its `package` campaign `--staged-package` |
| Kit | `kit-reference` | The reference inputs plus `--kit-executable`, `--kit-package`, `--kit-client-extension` and `--kit-resolver-extension`; optionally `--kit-core-extension` and `--kit-library-dir`; `--kit-release-package` for a released packman package |

`--help` describes every input; `tools/live/ci.py --config <worker config> --output <fresh dir> --seed 42 --dry-run` prints the complete command a CI profile runs. `--writer-fuzz-profile` selects the `ci`, `nightly`, `soak` or `package` writer campaign; `package` also needs `--staged-package`, the `<target-dir>/usd/omniverse/live` stage whose samples it runs. `--writer-plan` replays a retained root-field writer plan through `plugin-reference`, and `--reduced-plan` replays a recorded graph, rotation, period or staged-samples reduced plan ([Replaying a reduced writer plan](#replaying-a-reduced-writer-plan)), a staged-samples plan with the `--staged-package` its reduction recorded. `--list` also prints reserved names for future product suites; selecting one is an error, never a pass.

`--seed` sets the master seed; without it the runner draws and records a random one. Pull request CI runs every seeded check at seed 42, so a seed-dependent failure never blocks an unrelated change; a scheduled run of the `nightly` profile varies the seed on every run and records it ([CI guide](ovlive-ci.md#workflows)). `--timeout-ms` sets the per-suite failure watchdog (default 60 seconds; 300 seconds for `foundation`, longer for `writer-fuzz` and `kit-reference`), and `--max-output-bytes` caps each child log (default 1 MiB). These are harness limits, not product performance budgets.

Each run creates a `run-*` directory under `--artifact-dir` (default `../.cache/live-tests`) holding `manifest.json` (source fingerprint, identities, seeds, outcomes), `junit.xml`, bounded logs and `replay.json`. The runner keeps the 20 newest earlier runs and deletes older ones; `--keep-runs N` (minimum 2) changes that count, and the manifest lists pruned names. `--replay` re-runs the recorded suites, seed and inputs and refuses to run when the source fingerprint or any input identity differs. The exit status is 0 for a pass, 1 for a test failure, 2 for an infrastructure error such as a missing or stale input or a failed service start, and 130 for an interrupt; an infrastructure error is never a product result.

Repository shape checks are `git diff --check` and `python3 -B tools/release/check_format.py --clang-format <clang-format 18.1.1>`; they verify whitespace and C++ formatting, not runtime behavior. Do not edit native sources while a compiler runs: the object can hold older bytes with a newer timestamp, so force recompilation of affected inputs.

### Selecting suites and cases

[`tests/contracts/suites.json`](../tests/contracts/suites.json) catalogs every suite, implemented and planned: its product package, its tags, the fixture paths it consumes, the contracts of the [contract catalog](#coverage) it covers, its resource budget and the redaction its logs receive. Instead of `--suite`, `--tag` and `--package` each take a comma-separated list and select every implemented suite that carries one of the tags and belongs to one of the packages; planned suites are selected only by name. The tags are `pr` (the pull-request workflow), `sdk-free`, `native`, `reference` (the reference-service lanes), `campaign`, `manual` (`kit-reference`), `mandatory` (the CI profiles' mandatory suites) and `planned`; the packages are `harness`, `runtime`, `wire`, `scene`, `resolver`, `plugin`, `python`, `kit` and `reference`.

```sh
./tools/live/test.sh --tag pr --seed 42 \
  --uri-library ../.cache/components/liblive_uri_contract_probe.so \
  --wire-driver ../.cache/components/live_wire_envelope_test \
  --lock-driver ../.cache/components/live_lock_noalloc_test
./tools/live/test.sh --suite foundation --seed 42 --scenario test_runner,test_selection.CaseSelectionTests
./tools/live/test.sh --suite foundation --seed 42 --shard 0/4
./tools/live/test.sh --suite native-reference --seed 42 --driver-mode actor-auth-timeout \
  --reference-python ../.cache/live-reference-venv/bin/python --reference-openssl <path to openssl 3.5.9> \
  --unary-driver <build>/live_unary_driver
```

`--scenario` takes case IDs or dotted prefixes (a module, class or method), and `--shard I/N` runs the cases whose ID hashes to shard `I` of `N`, so the shards of one inventory partition it whatever the discovery order. Both apply to the suites that select cases, `foundation` and every reference lane except `kit-reference`; any other selected suite, a scenario that matches no case or a selection that keeps none is an error, never an empty pass. `--driver-mode` runs one diagnostic native driver mode as the only `native-reference` case against a fresh reference service; the catalog lists the modes, which no correctness test runs to completion. The manifest records the selection and `--replay` repeats it.

### Fingerprints, budgets and redaction

Each result in `manifest.json` records a `fixture_fingerprint`, a SHA-256 over the path and bytes of every file of the suite's catalog fixtures, and a `scenario_fingerprint`: over the case IDs the suite recorded, or, for a planned suite, over the ID and requirement text of each contract the catalog assigns it; it is null for an implemented suite that records no cases. `replay.json` keeps the fixture fingerprints, and `--replay` refuses a suite whose fixtures differ. `--list` prints each suite's package, tags and fingerprints.

A suite's `budget` bounds the bytes and files it adds to the run directory; a passing suite over either bound fails, and `resource_usage` records both. A suite's `redact` names patterns of the catalog's `redaction` table, which the runner replaces with `[redacted]` in the suite's log after it ends, keeping a prefix such as `Bearer `; `redactions` counts them. The reference lanes redact bearer tokens and PEM private keys, the credentials their fixtures create. These are harness limits and fixture policy, not product budgets or a real-service redaction policy.

### Service readiness and cleanup

A reference lane's workload reports readiness once a reference service it starts has answered a `Ping` through a real channel; the runner waits for that record under a 120-second failure-only watchdog. A workload that exits before it, reports a failed start or does not report in time has the outcome `service_start_failed`, with the reason, and never reaches its tests' evidence checks.

Each suite runs with a fresh `live-scratch-*` directory as its `TMPDIR`, `TMP`, `TEMP` and `LIVE_TEST_SCRATCH_DIR`. On Linux a subreaper guard owns its descendants; on Windows a Job Object contains the suite and every descendant before they run, with unhandled exceptions fatal rather than waiting on an error dialog. These guards end every descendant, including detached sessions, and remove the scratch directory when the suite ends, times out or is interrupted, or when the runner dies. On Windows a terminated job member stops counting as active, and leaves the job's process list, before its handles, its working directory among them, close; only its process handle's signal shows that they have. The job's completion port reports every process that joins it, through a nested job too, so the guard terminates the job and counts cleanup complete only once every reported process has exited or is gone. The port does not guarantee delivery, so cleanup is reported incomplete, never complete, when it reported fewer processes than the job counted or when a reported process cannot be checked, as it is when the 5-second failure-only bound expires first. On Windows, suites run in Python UTF-8 mode. macOS runs each workload in its own process group, signals that group on completion, timeout or interruption, drains output and removes scratch space. Descendants must remain in that group; cleanup after forced runner death and detached descendants is unqualified. Run manifests record `process_cleanup` as `process-group` or `descendant-tree`. Watchdog stack requests are Linux-only.

The macOS foundation inventory excludes exactly the following four cases from discovery before scenario/shard selection. `foundation.json` and the suite result record each excluded ID and reason. Exclusion names must exist in the discovered inventory; unexpected skips and expected failures still fail the selected suite. Linux and Windows run these cases.

- `test_foundation.SupervisorTests.test_successful_parent_reaps_detached_session`: cleanup after a successful workload leaves a detached child.
- `test_foundation.SupervisorTests.test_outer_timeout_reaps_nested_supervised_process`: cleanup of a nested supervisor in another session.
- `test_supervision.RunnerDeathTests.test_an_interrupted_runner_leaves_no_process_or_directory`: cleanup of a detached grandchild after interruption.
- `test_supervision.RunnerDeathTests.test_a_crashed_runner_leaves_no_process_or_directory`: cleanup of a detached grandchild after forced runner death.

### Replaying a reduced writer plan

`--reduced-plan` replays one recorded plan of a graph (`structural`, `samples`), rotation (`queued-rotations`, `queued-rotations-coalesced`, `uncertain-before`, `uncertain-after`), period (`long-rotations`, `stream-age`) or staged-samples (`staged-samples`) [writer reduction](#oracles): the `best.plan.json` or `original.plan.json` of a `<case>-reduction` directory, beside the `reduction.json` that recorded it. A root-field reduction's plans carry their own identities and replay with `--writer-plan`.

```sh
./tools/live/test.sh --reduced-plan ../.cache/live-tests/run-EXAMPLE/<case directory>/stream-age-reduction/best.plan.json \
  --reference-python <reference interpreter> --reference-openssl <path to openssl 3.5.9> \
  --plugin-driver <build>/live_plugin_driver
./tools/live/test.sh --reduced-plan <reduction directory>/best.plan.json --without-test-defect \
  --reference-python <reference interpreter> --reference-openssl <path to openssl 3.5.9> \
  --scene-transport-driver <build>/live_scene_transport_driver
./tools/live/test.sh --reduced-plan <case directory>/staged-samples-reduction/best.plan.json \
  --reference-python <reference interpreter> --reference-openssl <path to openssl 3.5.9> \
  --plugin-driver <build>/live_plugin_driver --staged-package <target-dir>/usd/omniverse/live
```

A reduction of these classes records in `reduction.json` a replay `context`: the case, its reference lane, the case scale a trial needs (a `stream-age` case's warm-up and memory bounds) and the identities its trials ran against, which are the source fingerprint, the native driver's manifest with its SDK trees, the reference-service dependencies and interpreter, and the sanitizer runtime; a `staged-samples` reduction adds `staged_package`, the stage its samples ran from: its path and manifest hash, the SDK interpreter the stage records, which runs the Python sample, and the sample executables and Python sample module with their hashes. A lane run outside the common runner lacks those identities, so its reduction records each as null and its plans are refused. The runner selects that lane, which needs the lane's usual inputs (`--plugin-driver` for `plugin-reference`, `--scene-transport-driver` for `scene-reference`) and, for a `staged-samples` plan, `--staged-package` naming the recorded stage, which no other class accepts, and before it launches anything requires the plan's hash to equal the one the reduction recorded for that file and every recorded identity to equal the current one; the lane checks both again before its service starts. It then runs the plan once through the evaluator its reducer uses, a fresh fixture, reference service and set of native writers, under the plan's master seed; OS scheduling is not replayed. A plan that carries a named test-only defect replays with it, so a self-test's reduction replays too, and `--without-test-defect` replays it without the defect. The run directory holds the verified copy in `reduced-plan`, the trial in `reduced-plan-replay`, the lane's `reduced-plan-result.json` and, in the suite's manifest result, `reduced_plan`; `--replay` of that run replays the same copy. The exit status is 1 when the trial raises the recorded signature, 2 when a valid replay does not, whether the trial passes, raises another signature or is unresolved, and 3 when the replay is refused (an invalid or altered plan or reduction record, including a malformed case scale or an absent identity, a changed identity, a usage error, including one of an abbreviated `--reduced-plan`) or produces no trial result; 130 is an interrupt. A long plan may need a longer `--timeout-ms` than the 60-second default.

## Local setup

The `foundation` suite needs no SDK and runs on Python 3.10 or later; CI runs it on Python 3.12, which the runtime and the Python package require.

**SDK-free component build.** The `uri`, `wire-envelope` and `lock-noalloc` suites need only CMake and a C++17 compiler. This is the component build the pull-request workflow runs:

```sh
cmake -S . -B ../.cache/components -DCMAKE_BUILD_TYPE=Debug -DLIVE_BUILD_WIRE=ON
cmake --build ../.cache/components --parallel 2
./tools/live/test.sh --suite uri,wire-envelope,lock-noalloc --seed 42 \
  --uri-library ../.cache/components/liblive_uri_contract_probe.so \
  --wire-driver ../.cache/components/live_wire_envelope_test \
  --lock-driver ../.cache/components/live_lock_noalloc_test
../.cache/components/live_uri_sanitize 42
```

`live_uri_sanitize` checks the native URI bounds with the given seed. The workflow also builds the same components with `-DLIVE_ENABLE_SANITIZERS=ON` in a separate job and runs `wire-envelope` and `lock-noalloc` under ASan and UBSan.

**Reference interpreter.** The reference-service suites take a Python 3.12 interpreter with grpcio and grpcio-tools 1.85.0 and protobuf 7.36.2, and an OpenSSL 3.5.9 executable; `tools/live/reference.py --identity` rejects other versions, the reference-service tests use Python 3.11 features and the `python-reference` suite imports the package's CPython 3.12 extension. Create this environment from a Python 3.12 that, on Linux, has the pidfd support the test process guard requires (`deps/live-tools.packman.xml` pins the one NVIDIA qualifies with):

```sh
python3.12 -B -m venv ../.cache/live-reference-venv
../.cache/live-reference-venv/bin/python -B -m pip install grpcio==1.85.0 grpcio-tools==1.85.0 protobuf==7.36.2
```

Pass `--reference-python ../.cache/live-reference-venv/bin/python` and `--reference-openssl <path to the openssl 3.5.9 executable>`. The `diagnostics-schema` suite's `--diagnostic-python` is a separate interpreter; the [snapshot schema](ovlive-diagnostic-schema.md#validating-a-snapshot) gives its recipe.

**Formatter.** The C++ format check expects clang-format 18.1.1, which `pip install clang-format==18.1.1` provides, as the pull-request workflow does. `python3 -B tools/release/check_format.py` runs the `clang-format` on `PATH`, or the executable `--clang-format` names.

## Test layers

A component pass is never reported as end-to-end coverage.

| Layer | Suites and checks | What it proves |
| --- | --- | --- |
| Pure Python harness | `foundation` (`tests/harness`), `uri` | The runner, reference models, codecs, reducers, repository rules and documentation pins; no SDK or service |
| Native component drivers | The native component suites above | Each component's invariants against stock-USD or model oracles, allocation faults and diagnostics output; no transport |
| Reference-service lanes | The reference-service suites above | Real gRPC over loopback: status mapping, TLS, fault recovery, reconnect and backend rotation, retained intent after lost replies, many-writer convergence |
| Plugin and package lanes | CTests `live_plugin_package`, `live_python_package`, `live_installed_package`; the install and inventory checks of `tools/live/ci.py` | The installed package loads in both orders, one runtime serves the C ABI, USD and Python, the native samples start from the install prefix, and inventory and notices are exact |
| Kit lane (manual-only) | `kit-reference` | One or two headless Kit processes attach live layers through `UsdContext`, author with plain USD, converge, survive backend rotation and retain edits after a lost reply |

The Kit lane is run by hand, because it needs a provisioned Kit and the unpublished companion extensions. It runs five tests under the `headless-overlay-reference-v2` profile and records the Kit build, selected inputs and startup runtime identity, so `--replay` rejects a different Kit. It qualifies either a build-tree package, bound to the checkout by its identity sidecars, or, with `--kit-release-package`, a released packman package verified from its zip checksum and release manifest; the inputs select the lane explicitly, and the evidence records the lane and the zip's SHA-256 ([Kit guide](ovlive-kit.md#validating-a-released-package)). The [Kit guide](ovlive-kit.md#running-the-kit-reference-lane) describes it from the Kit side.

## The reference service

`tests/reference_service/service.py` implements all ten LiveService RPCs independently of the client, sharing only the generated wire types. Test controls are Python objects, never an RPC or a listener in the plugin. Each case owns fresh state, ephemeral loopback listeners and a seed; synthetic principals set identity, permissions, token rotation and server-side expiry, which the service checks when each RPC starts, as the real service does; a rejection carries no message. An explicitly expired token stays expired whatever the wall clock reads, and only a deadline issued with a token compares against the clock, so a clock step cannot revive an expired token. An append-only ledger records every accepted create, update and delete with resource, incarnation, sequence, bytes and writer, so the ledger alone answers whether a mutation executed, and how often.

- **Named faults.** A fault plan targets an RPC method, attempt and boundary (`before_auth`, `before`, `after_commit` or `before_reply`) with a status failure or a pause gate, which proves whether a request committed before its reply was lost. Every planned fault must fire exactly once; an unused fault fails the case. `plan_unknown` loses one reply and fails the client's operation-ID re-send of it before the service evaluates it, which leaves the write's outcome unknown.
- **Operation IDs.** `UpdateLayer` and `CreateLayer` match a re-send by operation ID as the [design](ovlive-design.md#the-single-operation-id-re-send) describes: a request that applies its write replies `OPERATION_OUTCOME_APPLIED`, the same ID and content after a commit returns that commit's reply with `OPERATION_OUTCOME_ALREADY_COMMITTED` and records nothing, other content is `ALREADY_EXISTS`, and the identity and incarnation checks run first. Records are keyed as the service keys them: an update by session, layer, object and `client_id`, replaced by that writer's next write to the object, and a create by session and operation ID, kept through a replace or delete. An identified unchained update reads its writer's record as its start record once the whole call has been received, and a commit step that finds the record moved since, by the writer's next write or a `restore_checkpoint`, applies nothing and fails `UNAVAILABLE` without `ErrorInfo`, with the service's message starting "this attempt applied nothing, but an earlier attempt of this call may have committed" (`OVERTAKEN` in `operation_log`); the match of the call's own operation comes first. A chained update relies on its predecessor check instead. The `stale` write fault returns plain `UNAVAILABLE` while retaining the first attempt's commit work behind a release gate, and `stale_start` retains it before its start-record read; these faults exercise late-write ordering while the channel stays usable, independently of TCP reconnection availability. A `stale_start` released with a status drops its retained work before that read. The `delay_start` write fault holds a call before that read, as a handler waiting at upload admission with its body received does, and with a status set before its release fails the call with it, as the service drops a call still waiting at its deadline. Content is the SHA-256 over the layer name, a 0x00 byte and the concatenated payload, whatever the chunking. `operation_log` records each match. Setting `operation_ids` to false models a server older than operation IDs, which ignores them, applies every request and replies `OPERATION_OUTCOME_UNSPECIFIED`. `Ping` reports `operation_ids` and `chained_writes`: `advertise_capabilities` false reports neither, so the client neither chains nor re-sends, `chained_writes` false models a service with operation IDs but without chaining, and `pre_chaining` models a replica that refuses the chained header `INVALID_ARGUMENT` before reading any chunk while the `Ping` still reports chaining; a chained call whose operation ID is in `pre_chaining_operations` reaches such a replica once. A chained call waits for its predecessor after reading its content until it commits, its deadline or a cancellation, which drops it with nothing applied (`dropped` in `chain_log`); with `no_wait`, and in a stale commit step that runs after its call was answered, it is refused at once. A refusal's `last_record` is `absent` before any write and after `restore_checkpoint`, `operation` while the writer's record holds an operation ID and `no_operation_id` after a write without one, and the empty predecessor matches only `absent`. Every `INVALID_ARGUMENT` the service gives a recognized chained call carries an `INVALID_UPDATE` `ErrorInfo`. `arrival_log` records each identified update header with whether it is chained and `no_wait`, its monotonic arrival time and its cutoff, the time ahead of the call's deadline, by half the remaining time and at most 0.5 s, after which a waiting call is refused instead of committed, so the client receives the refusal before its deadline. The scene drivers report ready only once a `Ping` has reported their endpoint's capabilities, so whether a case's writes chain and re-send never races it.
- **Client keepalive.** `keepalive_interval_ms` (default `None`, a service without the client keepalive, which returns no interval and refuses a `JoinSessionKeepalive` frame `INVALID_ARGUMENT`) sets the interval returned to a join that sets `client_keepalive`. Such a join that receives nothing for three intervals ends `UNAVAILABLE` with the service's `google.rpc.ErrorInfo` reason `CLIENT_KEEPALIVE_TIMEOUT`, and its peers receive one `PeerLeft`. The keepalive clock moves only through `advance_keepalive_clock`, which ends every join that is due and returns their connection IDs, so a timeout happens exactly when a test advances it. Each request frame read restarts a join's timer; the service restarts it on any bytes of the stream, which the Python gRPC server does not expose below whole frames. `joins`, `keepalives` and `keepalive_timeouts` record each join's opt-in and interval, the keepalives each connection sent and the joins that timed out.
- **Merge owner.** `merge_owner` (default `False`, a service without the lease, which answers `merge_owner` false in `SessionConnected` and `Ping` and refuses a `MergeOwnerRequest` frame `INVALID_ARGUMENT`) models the advisory merge-owner lease of [design section 15](ovlive-design.md#15-sessions-presence-and-messages): a join that sets `JoinSessionHeader.merge_owner` negotiates it, each request is applied atomically and answered on the join's own stream, only the session's creator may claim, every grant takes the session's next epoch, the holder's join ending releases the lease, and every other negotiated join receives the change; a join that did not negotiate the lease never receives a `MergeOwnerState`. `evict(connection_id, release=True)` removes a join from presence as the service's sweep does and ends its stream `UNAVAILABLE`; with `release=False` the lease keeps naming the evicted join until the next claim takes it. `reject_principal(name)` answers that principal's later claims `UNAUTHENTICATED` without revoking a lease it holds, as an expired join credential is answered. A request without a known action or with `request_id` 0 ends the stream `INVALID_ARGUMENT`. `merge_owner_requests` records every valid request received; while `merge_owner_hold` is set, requests are recorded and left unanswered, so a test can end a connection or leave with one in flight. A connection in `merge_owner_linger` stays in presence after its stream ends, as a join the service has not yet noticed is gone, until `evict` removes it. `merge_owner_log` records every answer and announcement, and `joins` records each join's request and negotiation.
- **Second backend.** A second service instance shares the authoritative state, so a test can rotate a client to another backend under the same authority and check resume from a nonzero cursor.
- **HTTP/2 proxy.** `http2_proxy.py` forwards frames byte for byte and injects faults that an application-level status cannot reproduce: real stream resets, a graceful `GOAWAY`, and an ingress rejection of the next new streams, which it answers before the service with an HTTP 401 or a trailers-only `grpc-status` 16, as an authenticating ingress does. The rejected header block still reaches the service, whose HPACK decoder must consume it, ended by a field that marks it rejected, and the proxy then resets the stream; the reference service parks a marked call without running its handler until the reset cancels it, so a rejected request never reaches the service and never counts an attempt, as with Envoy ext_authz, which forwards nothing. It can terminate TLS with a per-case test certificate authority in front of plaintext backends, as the deployed ingress topology does, and `RotatingProxy` can too. It records frame metadata, never header or payload contents.
- **Scene profiles.** The base service treats layer content as opaque; `graph_service.py` adds the independent graph model, commits whole updates under the [service conflict rules](ovlive-design.md#service-conflict-rules) and generates snapshots and resume diffs. Before it processes an `UpdateLayer` or `CreateLayer` upload it counts the delta's entries as the service does and refuses one over its entry limits `INVALID_ARGUMENT` with the service's `google.rpc.ErrorInfo` (`DELTA_TOO_LARGE` or `CHILDREN_LIST_TOO_LONG`); `delta_entry_limit` and `children_list_limit` default to the service's 99,999 and 100,000, and a case lowers them below the profile's own record bound to reach the refusal. `refuse_updates` and `refuse_creates` plan UNAVAILABLE refusals of the next `UpdateLayer` or `CreateLayer` uploads that read each whole upload and apply nothing, with or without the service's `ErrorInfo` and a `google.rpc.RetryInfo` delay, and record each refused upload's operation ID, writer and payload digest; `creates` records every `CreateLayer` upload's operation ID, payload digest and arrival time.

The `reference-service` suite runs the service's self-tests. `--reference-python` and `--reference-openssl` are the interpreter and OpenSSL 3.5.9 executable that [local setup](#local-setup) describes; TLS fixtures use that OpenSSL to generate a test certificate authority and server certificates. It models no deployed authorization or durability policy; its fidelity limits are on the [support boundary](ovlive-support-boundary.md#supported-configuration).

To try the samples or the [Python quick start](ovlive-python.md#quick-start) without a deployed service, run the service alone from `client` with the reference interpreter: `<reference-python> -B tools/live/reference.py serve` listens on a free loopback port, or `--port N`, and prints one JSON line whose `authority` and `token` the samples take. It stops cleanly on Ctrl+C or SIGTERM, and with `--stop-on-eof` also when its standard input ends. It is a test fixture, not a deployable service: its state lives in memory for the process, and it accepts only the token it prints. The `reference-service` suite covers its start, token and shutdown.

## Oracles

No test derives its expected result from the code under test.

- **Graph model.** `tests/reference_service/scene_graph_wire.py` and `scene_graph_model.py` implement a bounded profile of all eleven spec types, the six structural commands, typed fields and time samples. Its value families are bool, int32, finite double, token, specifier, variability, token and path vectors, path list operations and the families Kit's presence layer authors: string and string array, token array, float, double array, and matrix4d, vec2f, vec3d and vec4f with their scalar and array forms. Floating-point families are held and compared by their exact IEEE-754 bits, so a sign-only or NaN-payload change is a change. Every other family, including a string that is not UTF-8 or holds NUL and a nonfinite scalar double, is rejected as `unsupported`, a profile boundary rather than evidence of malformed wire; truncation, trailing bytes, partial array elements and over-limit strings or arrays are rejected as `malformed` or `limit`. It commits updates under the [service conflict rules](ovlive-design.md#service-conflict-rules): by default a Reorder orders each child list it names as USD's `SdfApplyListOrdering` does, as the service from 0.2.0-rc.16 and the client's reader apply it, and field and sample data for a missing section is kept apart and never projected, as the client's reader drops it. `verbatim` commits a Reorder as Live Edit 0.1.x stores it, its list replacing the parent's whole children list, a non-child or repeat rejecting the update and an omitted child left unreachable; `adopt_orphans` gives a section the orphan data committed for its ID when a later Create or diff births it, as deployed services do. A delivered update, one a reader applies, ignores both. The graph reference service selects them with `reorder_rule` and `adopt_orphans`. It acks every catch-up at exactly the cut its content holds and delivers only later commits, as Live Edit 0.2.0 does; `unverified_cut` models a legacy Live Edit 0.1.x service that acks a fresh snapshot below commits it holds and delivers them again, and the tests that set it name themselves Live Edit 0.1.x coverage. `live_scene_graph_probe` applies the same bytes to the production `WireScene` builder, and `tests/native/scene/graph_reference.py` compares the outcome and entire state after every attempt.
- **Many-writer campaigns.** `writer-fuzz` runs seeded multiprocess campaigns (`ci`: 2 and 8 root writers, 4 graph writers; `nightly`: up to 32 root writers and 8 graph writers) against a fresh service per case. The `structural` case's plan (`structural_history.py`) draws each graph writer's 12 edits from its own seed, round by round, from these classes: a creation of the writer's branch under `/P` or `/Q` through one of three public constructor templates (a prim with a child, attribute and relationship; variant sets; connection and relationship targets), a write of the branch's leaf attribute or of `/P`'s shared field, a move of the branch to the other parent, a rename of the branch, which moves it to the end of its parent's children as the host's namespace rename does, a same-parent reorder that reverses `/P`'s prim children, and an erase of the branch. A field write's value is an `int32` or `float` scalar, a `vec3d` vector, a string, a token array or a `float` array, so one field takes values of several types in turn. Every generated plan holds every class and value family and a field written twice. Every name is unique, so no edit collides with another, and the sentinel children `/P/Child` and `/Q/Sentinel` remain. A move always changes parent, so it appends and compiles no Reorder. A rename or reorder compiles a Reorder that lists every current child of its parent, so it edits only `/P`, whose children are all prims, and no other edit of its round changes `/P`'s children: the Reorder then lists exactly the children the service holds when it commits, never an omitted or unknown one. A verbatim service's rejection of a listed ID that is not a current child, its unlisting of an omitted one, and the order across child lists of a parent with property children, which readers and a verbatim service give differently (design sections 9 and 20), therefore stay outside the case. Each round an independent peer also writes a root field, renames `/P` in three fixed rounds and, when the writer the round selects holds a branch, creates a child under it. The root-field and queued-rotation scenarios run twice: once with `usd-set-admit` binding one intent, and so one write, to each command (the root-field case also withholds chained writes), and once as `-coalesced` scenarios with chained writes advertised and plain USD change blocks, so each writer chains its writes behind a held one and coalesces blocks while its window is full; there every commit must be a contiguous run of one writer's edits, the last write of each field winning, and each writer's runs must cover its edits once, in order. `nightly` also runs one `long-rotations` case: 4 plugin writers with the production retry options through 500 event-driven rotations between two shared-state backends, each writer queuing one edit per outage, with every writer's first read retry at the first backoff step, any further retry in its consecutive attempt's window, one resume per writer and all writers converging after each rotation. In the other scenarios every service commit must match exactly one admitted edit or planned peer effect; in the `-coalesced` ones each must match one contiguous run of one writer's edits. Every admitted edit must end reflected, superseded, coalesced into a later edit of its run, rejected or retained for recovery, and all clients and a fresh observer must agree on complete typed scenes. The `soak` campaign runs one case: 4 plugin writers through 600 rotations with a 5-second READY pause between them, proactive token refresh on a 180-second lifetime, a server-side expiry every 100 rotations and a hold for a periodic `Ping` in one READY window every 100 rotations; its duration is the product of the count and the pause, the pause is load and never synchronization, and it asserts exact counts, logical gauges, threads and open files back to their warm-up values, gRPC's iomgr timer threads (`grpc_global_tim`), which gRPC only adds and keeps until shutdown, at most `SOAK_MAX_GRPC_TIMER_THREADS` apart from the other threads, and stated anonymous-RSS growth, slope and peak-RSS tolerances. The `ci` and `nightly` campaigns each run one `stream-age` case (100 and 600 periods), which compresses long sessions in time: 4 plugin writers read the layer and join its session through the HTTP/2 proxy in stream-age mode, which resets each stream with `RST_STREAM(CANCEL)` once it reaches the 240-minute ingress stream timeout on the proxy's stream clock, a clock the test advances by half the limit each period, so every second period ends every read and join on its open connection and the periods between show that no younger stream ends. Before each expiry the service stops accepting every token the writer has held, so every ended stream outlived its token; proactive refresh over wall time is the `soak` case's. Each period every writer authors one edit and sends one presence message and an independent peer commits; the period ends with exact accounting of commits, attempts and rejections, each message delivered once to every other writer, all writers converged, and retained-work gauges, threads and open files at their warm-up values, with anonymous-RSS bounds at campaign scale and the slope from 200 periods, fitted to each run of samples with an unchanged thread count, with the step at each thread-count change bounded per added thread. The `package` campaign runs one `staged-samples` case at seed 42 and one at a varying seed, with the samples of a stage that `tools/live/build.py` produced, run the way the [samples guide](ovlive-samples.md) and the [build guide](ovlive-build.md#using-the-package) give a user, with only that environment: the native and the Python participant each create a session and a `sample.live` layer, the Python one with the SDK interpreter the stage records, and 4 seeded plugin writers join the two layers, two each. In each of 8 rounds every participant authors one seeded edit and saves: a sample sets `/Example.value`, and a writer sets `/Example.value` or defines and then sets its own prim; every value is distinct. Every commit after a layer's creation must carry exactly one planned edit of that layer's participants in its round, each participant's edits must commit once and in order under one wire identity, and the service must have issued exactly two sessions, two layers and one update per edit, with no rejection. Every writer, a fresh observer per layer and each sample must show exactly the layer's prims with the last committed value of each, the samples through their `status` and `inspect` commands and an `export` of their own live layer that the SDK's Python reads, applied through the final sequence and holding no pending or buffered work; then the diagnostics sample must list exactly the two sample sessions, and every participant closes cleanly. On its first fixed seed the campaign also runs one `staged-samples-reduction` case, the class's reduction self-test ([writer reduction](#oracles)): 2 writers and 4 rounds under its own 600-second watchdog. Only the `presubmit` and `nightly` CI profiles build the stage, after their contract step, so they run this campaign as its own `package-samples` step ([CI guide](ovlive-ci.md#steps)); the client's `build.sh` and `test.sh` neither build a stage nor run the campaign.
- **Writer reduction.** A semantic mismatch in a root-field, structural or sample writer case retires the case's fixture and reduces its plan through fresh client and service trials (`writer_reduction.py`): a root-field plan by deleting single edits, and a structural or sample plan by deleting whole writers, rounds and the backend rotation after a round. Each structural or sample candidate is a selection of the seeded plan (`round_plans.py`), so it replays inputs the seed reproduces, and the reducer never proposes one whose retained edits need a deleted edit, such as a field edit on a branch no retained round creates, or a rename, reorder or erase whose branch the retained rounds leave under another parent than the one it was generated for, such as a reorder of `/P` without the move that took its branch there. Only the same signature may replace the candidate; a crash, watchdog expiry or other failure never does, and the original failure still fails the case. A mismatch counts, in a trial and in the failing case, only once the fixture releases its held faults and proxy gates and every native writer has closed through the checked path; a writer that cannot close or exited abnormally leaves the trial unresolved and the failing case unreduced, with the mismatch already recorded in its `-mismatch.json`. A structural or sample signature is the mismatch's reason and the first discrepant edit, in round and then writer order, so deleting a later discrepancy keeps it; a scene difference names, among the committed edits that changed the first differing node (one of its identities, or its children) or emitted a record at the first differing sample key, the latest in plan order, the first writer of the latest round, and a sequence gap the first admitted edit the ledger lacks, because the commit order within a round is OS-scheduled; detail that depends on the rest of the plan, such as every missing edit or the first differing scene path, is evidence, kept in each trial's `result.json` and the case's `structural-mismatch.json` or `samples-mismatch.json` and never compared. Two failures of a structural or sample case that no accounting raises reduce the same way. A backend rotation whose own check fails, a writer read generation that does not advance or writers that do not resume reading on the rotation's destination at the frontier before it, has the signature of its reason and `rotation`, the seeded ordinal of the round it follows; the resume check counts distinct writers by the client ID of the service's read records, not reads, so a second reconnect of one writer never covers another writer's wrong resume, and neither that reconnect nor the read order changes it; the rotation is the fault group a `rotation` unit deletes, while a round's write holds, indexed by UpdateLayer arrival, stay with their round, since without them a writer could compile against another writer's commit of the same round. A round whose commits stop short of its frontier, which the writers' convergence wait would end by timing out, is caught first by a service-side wait that the service's commits and call ends drive (`round_plans.stopped_short`): once no UpdateLayer call is in flight, no write was refused retryably in the round and every native writer process is alive, the ledger is final, and the signature is its reason, the class accounting's reason as `cause` and the first admitted edit, in plan order, that the ledger lacks. Without those conditions the stall is a watchdog or crash matter and has no signature. A writer whose convergence wait times out although the ledger reached the frontier is not reduced: the first commit it lacks holds whichever edit the OS scheduled at that sequence within the round, so no stable edit names it. At each convergence point a structural or sample case compares every writer's authoritative and then visible scene with the one the service ledger replays to, before the independent oracle (`round_plans.check_replicas`); a difference has the signature of its reason, the authoritative scenes before the visible ones, and the first in plan order of the edits the class's scene attribution names for each differing writer's first differing path. Which writers differ can depend on the commit order within a round, since a writer never reads its own commits, so the attribution reads only that node's identities, children and sample keys in the oracle's lineage, never the writer's position or the values it holds; the writers, paths and nodes are evidence. For the same reason the minimal plan of such a difference keeps a second writer, and a structural or sample reduction runs at most 24 trials. A nonzero wait result or pending count at that point raises a plain error and is not reduced: the first is the writer's own wait failing, a watchdog or transport matter, and no named defect leaves an intent pending once its writer has converged. The `queued-rotations`, `queued-rotations-coalesced`, `uncertain-before` and `uncertain-after` root-field cases run seeded round-based plans (`rotation_history.py`), in which every writer authors one root-field edit per round, and reduce a mismatch the same way, keeping it in `<case>-mismatch.json`. A `queued-rotations` rotation is the fault group between two phases of rounds (proxy park, held caught-up replies and the next phase's queued writes); once its writers have converged, writers that did not resume reading on its destination at the frontier before it give the structural and sample rotation signature, and a rotation after the last retained round leaves an empty phase, in which the writers only resume. In the uncertain cases the cut is the scenario, not a unit: each writer's first retained edit is its cut write, and the ledger must hold no write cut before execution, each write cut after its commit exactly once and no queued write; a failure's signature is its reason and the first discrepant edit in round and then writer order, so the commit order of the cut is evidence, and several unexplained commits are named by the least sorted field names. The oracle runs once the ledger is final: before the cut, when every UpdateLayer call the writers report issuing has reached the service and every call not held at its fault has ended (the service counts ended calls), and before the attempt and pending checks, which an issued queued write would also fail; and again once every cut handler has ended. A `queued-rotations` phase accounts its commits before checking their count, so a lost or repeated commit raises the accounting's mismatch. The root-field ledger accounting (`writer_history.account`), which these cases and the `root-fields` cases share, decides each class over the whole ledger and orders edits by seeded step (a round-based plan's round) and then seeded writer, which no deletion of edits, writers or rounds renumbers. Its signature is the reason and at most one name: a lost, repeated or FIFO-violating edit by the first such edit in that order, an unexplained commit by the least unexplained field name the plan authors, and a writer whose commits change wire identity, or writers sharing one, by the least such seeded writer, since the ledger does not say which commit carries the wrong identity and deleting another sharing writer must keep the name. A field no planned edit authors, a batched or empty update and a sequence gap with no lost edit name nothing; a lost edit's gap shows only if a later commit follows it, so it is evidence. Every other discrepancy, the gap and the commit contents are evidence, kept in each trial's `result.json` and the case's `writer-mismatch.json` or `<case>-mismatch.json`. In the coalesced form, which blocks coalesce into one commit, and so a commit's edits, its sequence and the first edit of a run that fails, depend on when the writer's window drains, so runs that fail to cover a writer's edits are named by the least such seeded writer, and an update mixing writers fails the coverage of every writer it touches, so one writer's value in another's run gives the same signature whether that run carries other edits or not. `queued-rotations-coalesced` reduces its accounting and rotation-check mismatches with these signatures; both backends run the fixture's service, so a defect fires on whichever backend a selection puts its round on, and a phase with more blocks than a writer's issuance window, which a selection that deletes a rotation can make, saves once a flush admits its buffered blocks. Its other checks, the pending and attempt ranges that bound how blocks coalesce and the oracle comparison after the accounting, raise plain errors and are not reduced: which blocks coalesce is OS-scheduled, so no stable edit or writer names a count outside its range. The chain and coalescing coverage of the coalesced mode applies to generated plans only, since a selection can retain too few queued blocks for either. The `stream-age` case runs a seeded period plan (`period_plans.py`), in which every writer authors one root-field edit per period and every second period ends every read and join stream; it accounts each period's writer commits with the root-field accounting and checks each expiry once every writer has resumed: each writer's first read resume after it is at a later stream generation, from the ledger's last sequence before the expiry. A read that resumes twice raises a plain error and is not reduced, since whether the second resume shares the first one's read batch or arrives in a later read is scheduling. A mismatch of either names the seeded `period` it was raised in, so its signature is the reason, that period and the accounting's own name, and the writers and records are evidence. Its reduction's first trial replays the plan cut after that period, which runs exactly the original's inputs through it, never the whole plan, so a cut plan that does not reproduce ends the reduction as `not_reproduced` and `reduction.json` records `truncated`; the reducer then deletes whole cycles, the two periods 2c + 1 and 2c + 2 of `cycle:<c>`, which keep each expiry's parity, and writers, but never the last cycle, which holds the failing period. A trial runs at the case's scale, and the warm-up baseline and memory bounds apply to generated plans only, since a selection can end before the warm-up. The stream-age case's other checks raise plain errors and are not reduced: the stream-age and soak RSS, slope, gauge, thread and file bounds measure resources, not a semantic discrepancy, and the ended-stream, rejoin, Ping, peer, message, convergence, attempt and authentication checks have no named defect yet. The `long-rotations` case runs the same period plan, one backend rotation per period, to B in odd periods and back to A in even ones, so every selection alternates backends. It accounts each rotation's writer commits with the root-field accounting before its plain commit count, and checks each rotation once every writer reports ready on the destination: at least one service read per writer resumed there at the ledger's frontier before the rotation. The service records each such read before its writer can report ready, and the check counts writers, not reads, so neither scheduling, a second reconnect nor read batching changes it. A mismatch of either names the seeded `period` and reduces as the stream-age case's does, from the plan cut after that period; both backends run the fixture's service, and the caught-up reply gate is armed by seeded period, so a cut plan runs exactly the original's inputs through it. Its other checks raise plain errors and are not reduced: a second read in a rotation, the retry and resume records a writer reads, its status and attempt counts, the per-rotation and teardown counts and writer identity across rotations either depend on how many reconnects the OS schedules or have no named defect, and the proxy, reply-gate and convergence waits are failure-only watchdogs. The `staged-samples` case runs a seeded plan (`staged_sample_history.py`) in which every participant, each participant sample and each seeded writer, authors one edit in every round, and accounts each sample layer's ledger after every round, so a mismatch is raised in the round that commits it. Its classes are decided over the whole layer in a fixed order: a commit that carries no single planned edit names the layer and the least path it writes that the layer's participants author, or only the layer when it writes none; a repeated, missing or misplaced edit names the first such edit in round and then participant order, the samples in creation order before the writers in seeded order; and a wire identity that changes within a participant, or that two participants share, names the first such participant. The commits, their sequences and every other discrepancy are evidence, kept in each trial's `result.json` and the case's `staged-samples-mismatch.json`. It reduces by deleting whole participant samples, each with its layer and the writers on it, writers and rounds; each candidate is a selection of the seeded plan, the reducer never proposes one in which a writer sets its prim without the round that defines it, and a reduction runs at most 24 trials. Its other checks raise plain errors and are not reduced: the attempt and rejection counts, the service's scene against the one its accounted commits make, every writer's, observer's and sample's convergence wait and status, the diagnostics listing and each participant's close have no named defect or are failure-only watchdogs. `soak` is not run through reduction: its rotations share these checks and raise the same signatures, but its expiry, Ping-hold and warm-up cadence counts the rotations run, its token refresh runs on wall time, and its resource bounds are not semantic discrepancies. The `writer-reduction`, `structural-reduction`, `samples-reduction` or `<case>-reduction` directory holds `original.plan.json`, every trial's plan and result, `best.plan.json` and `reduction.json`, whose `deletion_minimal` is true only after a complete pass without unresolved trials. Reduction runs inside the failing case under its watchdog, and every file is written before the trial it records starts, so a run the watchdog ends keeps `status` `running` with that trial's `result.json` `pending`, and `best.plan.json` is the smallest plan reproduced so far. A named test-only defect qualifies each class: `plugin-reference` corrupts one root-field edit, forwards the queued-rotation rotation after round 7 to the backend it leaves, in both the plain and the coalesced case, commits -1 for writer 0's round-6 owned edit in the coalesced case, whichever run carries it, and applies writer 0's round-0 write when the cut cancels its handler held before execution or passes it through its commit step without committing it, or releases that write, held after its commit, before the cut while writer 0 has queued writes, which then follow it, in a stream-age plan commits -1 for writer 0's edit of period 5 and commits a peer edit the period's frontier does not count before the expiry of period 6, in a long-rotations plan commits -1 for writer 0's edit of rotation 5, on backend B, and forwards rotation 6 to the backend it leaves, and `scene-reference` corrupts one structural shared-field write, one structural reorder, which it commits with its list reversed, and one sample record, acknowledges one sample edit without committing it, forwards one sample rotation to the backend it leaves, and relays every structural shared-field write, and every sample at time 3.0 of section 6, to readers with the value -1 while its ledger keeps the uploaded value, and the `package` campaign's `staged-samples-reduction` case commits -1 for writer 0's round-2 edit; each self-test reduces to the minimal plan, replays it to the same signature and passes it without the defect, and the staged-samples self-test also passes its whole plan without the defect. The structural self-tests run the seed-42 structural plan whatever the master seed, since their minimal plans depend on the edits the seed draws. The structural corrupt and reorder, structural and sample relay, `uncertain-before`, `stream-age` corrupt and staged-samples self-tests also replay their recorded `best.plan.json` and `original.plan.json` through the standalone `--reduced-plan` command, with and without the defect, and check that it refuses an altered plan or recorded hash.
- **Reducer.** On a mismatch, `graph_reduction.py` keeps the original evidence and shrinks the failing prefix by deleting batches, commands, fields and sample records. Each trial is a fresh process; only the same first discrepancy at the same original edit may replace the candidate, and a crash or watchdog expiry never does. `reduction/reduction.json` names the payloads; `deletion_minimal` is true only after a complete fixed-point pass.

## Determinism rules

These rules apply to every correctness test.

- **Barriers, not sleeps.** Establish the state under test with fake clocks, controllable schedulers, events, barriers or service pause gates, never with a sleep, elapsed time or timeout expiry. A healthy test finishes as soon as its assertions can run. When a dependency's timing cannot be controlled, add an observable event or test seam.
- **Failure-only watchdogs.** Real-time timeouts only catch hangs; no passing path waits for one. Real clocks belong only in performance measurements.
- **Seeds before workers.** Record the master seed, per-writer derived seeds and the generated operation plan before any worker starts, so a crash cannot hide its seed. A seed reproduces generated inputs and scheduler choices, not OS thread scheduling.
- **No retry into a pass.** A failed run keeps its evidence; a diagnostic rerun is a new run with its own seed and artifacts.

When a runner watchdog expires on Linux, the runner asks every descendant process that installed a stack-dump handler for its thread stacks, waits at most 3 seconds, then kills the tree; Windows has no signal to request stacks with, so there the runner kills the tree without dumps; the outcome stays `timeout`. Native test drivers install the handler, and Python test entry points register `faulthandler`, only when `LIVE_STACK_DUMP_PREFIX` is set, which the runner sets per suite and per CI step. On Linux and macOS a Python entry point's handler also writes every thread's stack to its dump when the process dies of a fatal signal, so a crash such as the reference service's segmentation fault leaves a listed dump; the reference service installs its handler before it loads OpenSSL, so a fault during those imports does too. Dumps are `<index>.stacks.<pid>` beside the suite log (`<step>.stacks.<pid>` for a CI step) and every non-empty dump is listed as `stack_dumps` in `manifest.json` and the CI summary whatever the outcome, including one a driver's in-process watchdog writes before it aborts; a run removes dumps an earlier run left at its prefix. A native dump lists each thread's frames between `live-stack-thread` and a final `live-stack-dump end` line whose `missing` counts the dump's threads, the one that took the SIGQUIT among them, that wrote no block within 2 seconds, including ThreadSanitizer's own runtime thread. Each dump's thread signal carries the dump's generation, so a thread's block counts toward the dump it answers and only while that dump is open: an answer to an earlier dump, or one after its dump's end line, writes nothing. The thread that took the SIGQUIT writes its block first, and a dump never starts on a thread that is still answering one. A fault in a thread's unwinding, such as following a frame whose unwind information is not accurate at the interrupted instruction, is contained to that thread: its block holds the frames reached before the fault and a `live-stack-unwind-fault signal=<n>` line, and the dump goes on to its end line; frames of a driver without exported symbols print as offsets, which `addr2line -f -C -e <driver> <offset>` resolves. Python processes show Python frames only.

A build-path change needs plugin loading, native sample and Python import checks from outside the source tree. Credentials, GPU and deployed-service access are never ordinary CI inputs. Report an unavailable local capability; never skip it into a pass.

A passing path waits out a real deadline only when that deadline's expiry is the behavior under test and the outcome is classified deterministically before the wait can matter: either credential starvation is recorded before a 1 ms deadline, the minimum the API accepts (`actor-auth-wait-open-deadline`, `public-deadline-starved`, `join-auth-deadline`, `--discovery-auth-deadline` and the resolver authentication deadline), or the completion the deadline bounds cannot arrive because a pause gate, a held host gate, a missing credential or a hung fixture holds it (the client RPC deadline, metadata deadline, read and rejoin first-response deadlines, auth-wait, bounded-wait and runner-watchdog cases). Sleeps and fixed windows are never synchronization: every other real-time bound is a failure-only watchdog, and a polling loop spins only on an observable predicate under one. No correctness test establishes its state by elapsed time; peer departure, actor idleness, layer readiness, the prepared-activation deadline (`--prepared-timeout`, which expires the initial-open deadline through `SceneAttachment::expireActivationForTest` while the bootstrap is held) and a read attempt's first-response deadline (the scene driver's `expire-read`, which expires it through `SceneAttachment::expireReadForTest` while a pause gate holds the response) each have a test seam or a status callback. The `actor-auth-timeout` native driver mode lets a real token expire on purpose; it probes the auth terminal watchdog: campaigns run the mode repeatedly, and an expiry of its worker-idle or terminal watchdog, which the `actor-auth-expiry-*` modes share, logs its `auth-idle-watchdog` or `auth-terminal-watchdog` line with the actor's and endpoint's auth state and writes the driver's stack dump before the driver aborts, so one with no identified cause leaves evidence. No correctness test lets its token expire; one test runs it, and `actor-auth-expiry-idle`, with `LIVE_TEST_EXPIRE_AUTH_IDLE_WATCHDOG`, which expires the worker-idle watchdog at once, to check that report.

## Coverage

[`tests/contracts/catalog.json`](../tests/contracts/catalog.json) maps each required behavior to the tests that cover it. Each contract has an `id`, an owning area (from core scene semantics and ABI loading to recovery, thread safety, Kit and packaging), the `requirement`, a `status`, whether it is `release_required`, the `cases` (test files or `file::Class.test` names) and a `coverage_limit` stating what the cases do not reach.

`foundation` checks that every case path exists and that each status agrees with its cases. Coverage is counted in contracts and state transitions, not test counts or line coverage. When you add behavior, extend its contract and name the cases; record what they cannot reach in `coverage_limit`.

## Sanitizers

The `asan` profile of `tools/live/ci.py` builds every native lane with AddressSanitizer and UndefinedBehaviorSanitizer (`LIVE_SANITIZER=address`) and runs them with leak detection on. `tools/live/sanitizer.py` owns the runtime recipe: `detect_leaks=1`, full unwinding on allocation (the USD SDK has no frame pointers) and `halt_on_error=1`. The `tsan` profile builds the same lanes with ThreadSanitizer (`LIVE_SANITIZER=thread`; `LIVE_ENABLE_SANITIZERS=ON` is an alias for `LIVE_SANITIZER=address`) and runs them under `setarch <machine> -R`, where `<machine>` is the host's `x86_64` or `aarch64`; every report is logged per process under the run directory with `halt_on_error=0`, the process still exits nonzero, and the runner fails any suite that leaves a report file. Suite reports are `<run>/<index>.tsan.<pid>` and step-level reports are `<output>/tsan.<pid>`; each suite's `sanitizer_reports` in `manifest.json` lists its files, and `halt_on_error=0` with exit code 66 makes the run red.

`tools/live/lsan.supp` and `tools/live/tsan.supp` follow fixed rules, which `tests/harness/test_sanitizer.py` enforces:

- LeakSanitizer entries name third-party USD or TBB allocating frames, or statically linked OpenSSL frames by function or source file, only; never libstdc++ or allocator frames.
- Each `race:`, `called_from_lib:`, `mutex:` or `deadlock:` entry names a third-party frame: prebuilt USD and TBB, statically linked gRPC, absl, upb and OpenSSL, the glibc dynamic loader, or a third-party header template inlined into our code; an entry never names a product frame.
- Each entry follows a comment giving its owner and reason.
- A path-keyed entry names a third-party source tree (OpenSSL's `/src/crypto/`, `/src/ssl/` or `/src/providers/`, USD's `/pxr/`, gRPC's `/src/core/`, glibc's `/nptl/` or `/sysdeps/`), never a product or test tree; an entry anchored at both ends (`^name$`) names one bare third-party C symbol, never a namespaced, templated or mangled C++ name or a product C API name.
- A leak whose allocation site is `omni::usd::live` or a `live_*` binary is a product or test defect to fix, never a suppression.
- A ThreadSanitizer report whose happens-before edge runs through uninstrumented third-party code (a handoff or a lock inside a prebuilt library) may be keyed on that third-party frame only; a report with both accesses in product code and no third-party edge is a product or test defect to fix or annotate, never a suppression.

USD's `TfNotice::Register` allocates its deliverer in a header template compiled into our binaries and loses it when the notice registry's own allocation throws. A suppression would have to name the product frame that inlines it, so the product's one registration, in `BoundLayer::ensureSetup`, runs inside a LeakSanitizer disabled scope (`__lsan::ScopedDisabler`, address builds only) instead. LeakSanitizer treats allocations in that scope as roots, and the lost deliverer's weak pointers reference the `BoundLayer`, the layer's live state, so the scope also hides a product leak of that state and everything it owns on the fault path; the `asan` scene lane's zero-report run of the allocation-fault sweep of the live format's Read, which reaches that path, is what shows the state is freed.

LeakSanitizer matches an entry against every frame of a stack, so each entry also hides leaks that pass through that frame. A ThreadSanitizer `race:` entry matches a function, file or module name in any frame of the racing access stacks (or a global variable's name or module), never a heap allocation stack or a thread creation stack, so each entry also hides a product race whose access stack passes through it; that cost is why both lists stay short. A `race:` or `called_from_lib:` entry that names a module names exactly one library.

No `race:` entry names a USD module. The USD-linked test executables (`live_scene_transport_driver`, `live_wire_scene_test`) keep the standard allocator under ThreadSanitizer, so USD calls it directly and `called_from_lib` ignores its allocations; their allocation-fault cases run only in the other profiles. The remaining USD entries key on USD 25.11 header templates compiled into our binaries (`VtValue`, `TfDelegatedCountPtr` and its count hooks, `TfToken`, `TfPointerAndBits`, `VtDictionary` and the `TfRefPtr` counters), anchored with `^` at the start of the frame's function name so that none matches a product function that only takes or returns a USD type. Each hides a race whose access runs inside that template, including one reached from product code: `HostSceneStorage::_VisitSpecs`, `WireSceneBuilder::build`, `buildSceneCandidate`, the layer actor's and scene journal's value handling, and wire value decoding. Two USD entries key on other third-party frames: the `PcpLayerStack` frame in `libusd_pcp`, whose constructor and destructor call the `std::shared_ptr` count templates our executables export, and libstdc++'s out-of-line `std::string::find`, which uninstrumented USD code calls on TBB workers on strings a host thread built; the second also hides any other race whose racing read is that libstdc++ function. The gRPC entries never match the `grpc_schema_probe.cpp` test file, the `live_grpc_schema_probe` module or a product function that only takes a gRPC C++ type: C symbols and the C++ API are anchored at the start of the function name, gRPC C types match only inside a parameter list, and the C++ API otherwise matches only as a template argument or in `grpc::internal`. gRPC's TLS teardown functions `ssl_protector_destroy` and `secure_endpoint_unref`, which free the frame protector and the secure endpoint on an event-engine thread after gRPC's uninstrumented last unref, are anchored at the start and closed by their parameter list's opening parenthesis, so each names that one function. Those two entries rest on the racing addresses, which lie inside gRPC's frame-protector and secure-endpoint objects, because ThreadSanitizer does not restore the previous-write stacks of those races. Product code that hands an object to uninstrumented code annotates the handoff instead: the completion-queue tags (`submitTag`, whose release is the last access before completion) and a `HostSceneProjection`'s publication to USD. The `tsan` profile refuses the `kit-25.11` USD profile, whose libraries and namespace these entries do not name.

## Windows checked-STL allocation faults

Windows stock debug builds use MSVC checked STL. Its default vector constructor and string move constructor allocate iterator proxies inside `noexcept` operations: a whole-heap test fault there terminates the process before a surrounding `bad_alloc` handler can run. The debug companion therefore has the explicitly narrower [support boundary](ovlive-support-boundary.md#supported-configuration); release and sanitizer fault-injection tests remain required. Windows native test failures write CRT assertions and exception text to stderr with at most 32 current-thread stack locations using local PDB symbols; symbol-server lookup is disabled, and termination remains a failure. The foundation failure-output control deliberately asserts and throws and requires nonzero exits and captured diagnostics.

## Interactive edit benchmark

`tools/live/edit_benchmark.py` measures sustained interactive editing against the omni.client live layer path: the time from a host edit to its visibility at a peer, the turns per second a writer publishes, and its backlog. It is a characterization, never a CI or presubmit gate, and it asserts nothing; it writes `results.json` and `summary.md`, whose last table compares ovlive with the baseline measurement by measurement. Results belong on pull requests, not in this guide; the [benchmarks guide](ovlive-benchmarks.md#recorded-edit-benchmark-results) records the run the support boundary cites.

**Acceptance bar.** ovlive at least matches Omniverse Client Library 2.74.0 driven as the pipelined baseline, one coalesced update per frame with at most 16 in flight as omni-spectree's default live layer format drives it, with its USD host cost (the `client-library` writer below), at 20, 50 and 100 ms of added round trip with the Kit-frame ovlive writer described below. For the sustained `single` and `multi` scenarios the bar is edit-to-peer latency (p50 and p99) and published throughput. For the `burst`, `multi-burst` and `batch-in-one-frame` scenarios it is edit-to-peer latency (p50 and p99) only, because the Kit-frame writer runs a flush round trip every frame, which caps burst throughput by construction, so burst throughput compares unlike things. Every scenario also requires complete delivery on both sides: the writer accepts every turn it authors, the peer sees every accepted turn, no write fails and the writer drains. Latency covers only the turns a peer saw, so a run that refused or lost its slowest turns would otherwise look faster; an incomplete ovlive run misses the bar, and an incomplete baseline is no bar to meet, so that comparison misses the bar until a rerun delivers every turn. The baseline is 2.74.0 because it keeps several `UpdateLayer` calls in flight per object; 2.75.0 and 2.75.1 send one write per object at a time, a weaker baseline, and 2.76.0 restores 2.74.0's throughput.

To re-check the bar, build the ovlive revision under test (`./build.sh` puts its Python extension under `../.cache/local/build`), obtain the Omniverse Client Library 2.74.0 package for `manylinux_2_35_x86_64`, and run the benchmark with the reference-service interpreter, which has `grpcio`, `grpcio-tools` and `protobuf`. `--python-extension` names the build's `_live` module and `--client-library` the package root, the directory that holds `release/bindings-python`:

```sh
<reference python> tools/live/edit_benchmark.py --seed 42 \
  --python-extension ../.cache/local/build/plugin/omni_usd_live/python/omni/usd/live/_live.cpython-312-x86_64-linux-gnu.so \
  --client-library <installed omni_client_library 2.74.0 directory> \
  --scenarios single,multi,burst,multi-burst,batch-in-one-frame --rtt-ms 20,50,100 \
  --label ovlive=<revision> --label baseline=omni_client_library_2.74.0
```

For an ovlive-only orchestration smoke run without the baseline package, use `--clients ovlive --no-client-library-reader --scenarios single --rtt-ms 0 --jitter-ms 0 --duration-s 1`. The extension must come from the build tree with its adjacent SDK identity manifest; an installed module without that manifest is not a benchmark input. This run checks writer, peer, proxy and report generation and makes no baseline comparison.

The bar holds when every row of the summary's comparison table reads `yes` under "Meets the bar", that is, when no cell in the bar carries a `(worse)` or `(incomplete)` mark; the "Turns delivered" column counts the turns each side's peer saw of the turns it authored, and a row that misses the bar through incomplete delivery names the incomplete side. p95, backlog and burst throughput cells carry an `(info)` mark and never decide it. A row whose baseline writer reports a client library version other than 2.74.0, with any build suffix, reads `no (baseline <version>, not 2.74.0)`; such a run characterizes that version and decides no bar. To check a build outside this checkout, point `--python-extension` at that build's `plugin/omni_usd_live/python/omni/usd/live/_live.cpython-312-x86_64-linux-gnu.so`; the benchmark loads the `omni_usd_live` plugin package that contains it and the USD libraries named by the `.manifest.json` beside it. Before any case runs, the benchmark fails unless the extension, the plugin artifacts and the SDK trees hash as that manifest records; it does not compare sources with the checkout it runs from.

Each case starts fresh processes: a reference service, a TCP proxy in front of it, a raw `SubscribeReadLayer` peer, an Omniverse Client Library peer and one writer, every client connecting through the proxy. The proxy adds half the round trip in each direction plus a uniform per-chunk jitter (`--jitter-ms`, default 2) drawn from generators seeded by `--seed`, and never reorders bytes. The service is the reference `LiveService` relaying each payload verbatim in the Live Edit service's per-commit catch-up mode (`--service opaque`, the default), with the capability queries Omniverse Client Library makes before using a direct endpoint; `--service graph` uses the graph reference service instead, whose per-commit validation costs tens of milliseconds for the multi-prim scene and dominates every client. The layer is created before the writer starts, with prims `/P<i>` holding double attributes `a<j>`; a turn sets every attribute's default to the turn number, which the peers decode to see which turns are visible.

| Scenario | Turns |
| --- | --- |
| `single` | 60 Hz for `--duration-s` (default 10), one attribute per turn |
| `multi` | 60 Hz for `--duration-s`, 50 prims with 3 attributes each per turn |
| `burst` | `--burst-turns` (default 1,000) one-attribute turns back to back |
| `multi-burst` | `--burst-turns` turns of 50 prims with 3 attributes each, back to back |
| `batch-in-one-frame` | `--burst-turns` change blocks of 50 prims with 3 attributes each inside one frame, as a script authoring a large batch does; it reports how many turns each writer accepts |

`--rtt-ms` selects the added round trips (default 20, 50 and 100) and `--clients` the writers. `--rate-hz` changes the sustained rate, so a sweep at `--rtt-ms 0` finds a client's CPU ceiling, and `--scene-prims` grows the layer with prims the turns never edit, which shows how per-update cost depends on layer size; the `client-library` writer's host layer holds the same scene. `--writer-wrapper` runs the writer under a command prefix such as a sampling profiler, with `{dir}` expanding to the case directory. `--service-option NAME=VALUE`, repeatable, sets a reference service state attribute, such as `chained_writes=false` to measure ovlive against a service without chained writes. `--diagnostics reduced` initializes the ovlive writer's runtime with diagnostic history disabled (`DISABLE_DIAGNOSTIC_HISTORY`) and the minimum severity at `ERROR`, so a run against the default `--diagnostics default` measures the instrumentation's cost; the report records which one ran. The benchmark uses the reference service and protocol of the checkout it runs from, so a revision whose protocol differs runs that revision's copy of the benchmark.

- **`ovlive`** drives the ovlive under test through its Python bindings as a USD host. Each turn models a Kit frame: the main thread authors the turn in one `Sdf.ChangeBlock`, then runs host jobs until the flush job that turn requested has been dispatched and run, waiting at most `--frame-wait-ms` (default 2) because the job reaches the host queue from the runtime's thread. A batch runs the jobs once, after its last turn. A USD call the layer refuses, such as one past the host edit buffer quota, is recorded as a refused turn and the run continues.
- **`client-library`** models omni-spectree's default live layer format on the real Omniverse Client Library, host cost included. The host authors each turn into an in-memory `Sdf` layer with the same USD calls and change block as the ovlive writer, a change-notice listener and the writer record which specs changed, and each tick builds the delta from those specs' current values in the layer and encodes it. Edits since the last tick coalesce into one update, sent at the tick only while fewer than 16 updates are unacknowledged (`PENDING_UPDATES_STOP_COUNT`), and otherwise kept buffered. A sustained scenario ticks at 60 Hz, a burst once per turn and a batch once after its last turn. It authors with the USD SDK of the ovlive build that `--python-extension` names, and it encodes with the reference graph profile's Python encoder, which costs more per field than omni-spectree's native encoder.
- **`client-library-record`** is the same write pattern without host USD work: each turn only records its values, so its authoring rate is far above any USD host's. It is kept for continuity with earlier results and is outside the acceptance bar. Client library 2.74.0 keeps several `UpdateLayer` calls in flight per layer; 2.75.0 and 2.75.1 send one at a time.

A turn's latency runs from the moment the writer authors it to the first update at the peer that holds it or a later turn, and, with the opaque service, splits at that update's commit into edit-to-commit and commit-to-peer times; the graph service records no commit times, so its cases have no split. Readers record arrival times and decode after the read ends, so decoding never delays an arrival. The raw reader gives the primary latencies; the Omniverse Client Library reader applies that library's default jitter reduction, calling `omni.client.live_process` every millisecond, and gives the secondary column. Published turns per second is the turn count over the time from the first edit to the last turn's visibility, the backlog is the most turns authored and not yet visible at any edit, and turns per update shows coalescing. The writer peak reports ovlive's `pending_write_count`, `buffered_edit_count` and turns spent `BLOCKED`, with the snapshot's `layer_writes` window metrics when the build reports them, or the baseline's updates in flight and buffered turns, followed by each writer process's peak resident set (`ru_maxrss`) and CPU time when the platform has `getrusage`; an ovlive writer's results also keep its diagnostic metrics and most recent records.

Each run writes `results.json`, `summary.md` and one directory per case with the raw timelines, `metrics.json` and the process logs under `--output` (default `../.cache/edit-benchmark/run-*`). `results.json` records what it measured under `identities`: the ovlive extension path with the full SDK identity manifest beside it, which also names the USD libraries the `client-library` writer authors with, and the Omniverse Client Library package path with the version and build string it reports; the run fails after writing its results if a baseline writer reports another version. Each case's metrics carry a `delivery` record of authored, visible and refused turns, failed writes, drain and whether the drain timed out, where an ovlive layer that fails counts the write that failed it, and each comparison carries both sides' records and the incomplete sides. Times are wall-clock measurements of real processes on one host, so repeated runs vary; seeds fix the workload and the proxy jitter, not the timings. The baseline is a model of omni-spectree's write pattern on the real library, not omni-spectree itself: it encodes the same graph wire profile as the reference service, never reads its own layer and settles an update when its callback arrives.

## Known test-environment issues

Kit's frame-rate limiter can request multi-second sleeps after the realtime clock jumps relative to the monotonic clock, which stalls a Kit process with pending work; run Kit on a host with a stable realtime clock. The intermittent SIGSEGV at process exit comes from the TBB thread-naming observer in stock `omni.tbb.globalcontrol`, and the companion `omni.usd.core` overlay, selected in the reference lane with `--kit-core-extension`, fixes it.

On Windows the C runtime flushes buffered standard output only in its own process detach, after `ExitProcess` has ended every other thread of the process. A process can end before that flush, with its exit code, when another thread is still exiting at that moment, as gRPC's threads still are for about two milliseconds after the runtime shuts down, or when a library's process detach enters a lock that a terminated thread held; a driver's final record then arrives cut at a multiple of the 4 KiB buffer, or not at all. Every native test driver links `tests/native/support/StackDump.cpp`, which leaves its standard output unbuffered on Windows, and the samples flush each record as they write it. `tests/harness/test_exit_flush.py`, in `foundation`, reproduces such an exit on every pull request's Windows runner and checks both disciplines.

A staged participant that acknowledges `close` but does not exit within the existing ten-second watchdog remains a test failure. Its artifacts record the PID, process/pipe state and, on Windows, a normal minidump with thread information plus matching local images and available PDBs. Collection runs in a separate process with a twenty-second failure-only bound; a capture error cannot turn the shutdown timeout into a pass. The private CI evidence audience and retention apply to these files. The foundation failure-output control captures a waiting child and verifies the dump header and nonempty thread stream. This distinguishes an exit stall from a convergence mismatch without changing the participant or its success condition.

## Allocation and edit-boundary probes

Two opt-in diagnostics reproduce the USD boundaries of [failure containment](ovlive-design.md#failure-containment). Both are outside the default build and CTest, and neither is a safety pass: each report records `product_qualified: false`.

The edit-boundary probe reproduces the known USD limitations beside a successful namespace-move control. Build the explicit target in a configured scene-SDK build and run the supervised driver:

```sh
cmake --build "$BUILD" --target live_usd_edit_boundary_probe
python3 -B tools/live/usd_edit_boundary.py --driver "$BUILD/live_usd_edit_boundary_probe" --artifact-dir ../.cache/usd-edit-boundary
```

Each case runs in a fresh process; the runner validates manifests before and after, identifies the loaded Sdf library, and exits zero when the limitations reproduce. On USD 25.11 and Kit USD `0.25.11.kit.5-gl.21209`, it shows that ignoring a data move leaves `/P` in storage while USD moves a retained handle to a nonexistent `/Q` and returns success, and that a delegate that disables editing still allows the current field write.

`tools/live/usd_allocation.py`, with `--driver` naming the built `live_wire_scene_test` and a required `--artifact-dir`, injects one C++ allocation failure on the calling thread during a complete public USD operation and compares stock SdfData with the live projection under the same seeded layer, stage and retained handles. `--operation` selects namespace move, child creation, field, dictionary or time-sample edits, `--backing` selects `stock` or `projection`, and `--controls-only` runs only the uninjected controls. Each injection index runs in its own child; a crash, truncated output or failed cleanup cannot finish a sweep, and the ten-second bound is a failure-only watchdog. `complete: true` means every sweep reached a clean uninjected success past the observed allocation sites. The campaign covers calling-thread `new`, not every SDK allocator.

The `runtime-foundation` and `scene-reference` lanes sweep every allocation before a live layer's first RPC (actor open, `SdfLayer::New` of the live format, and the `Read` hook up to its bootstrap wait) and require each failure to report `RESOURCE_EXHAUSTED` or propagate the allocation exception, and to leave nothing behind; the probe above shows why no lane can sweep inside a complete USD operation. The `SdfLayer::New` sweep continues under a fresh layer identifier after each throw, because a failure inside USD's own layer constructor leaves a dead layer-registry entry that aborts a later layer of that identifier.
