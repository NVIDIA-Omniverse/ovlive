# Support boundary

This page states what ovlive supports, how it is tested against Live Services, which qualification gates are open, and the limitations a host or user meets today. It is for engineers deciding whether ovlive fits their host and for contributors picking up open work; the [design](ovlive-design.md) states the behavior and the [testing guide](ovlive-testing.md) describes the lanes.

## Supported configuration

ovlive is one C++ runtime in the `omni_usd_live` library that serves the USD `.live` file format and `live://` resolver, the C ABI (`omniUsdLive*`) and the Python API (`omni.usd.live`). The supported targets are the Kit USD 25.11 build on Linux x86-64, Linux aarch64 and Windows x86-64 and the stock USD 25.11 build on Linux x86-64, of the [build guide](ovlive-build.md), all with Python 3.12. The Kit extension runs on an internal Kit build with the companion extensions; it does not start on stock public Kit 110.3, whose stock USD a `kit-25.11` package does not bind to ([Kit guide](ovlive-kit.md#what-works-with-a-public-kit-build)). A release is the experimental prerelease of the [release procedure](ovlive-release.md): the source archive and, for each target, one packman package zip, packed from the qualified `ovlive-<version>-<usd-profile>-<platform>.tar.gz` archive of the [build guide](ovlive-build.md#release-archive), which is a qualification record and not a release asset; it is not signed.

Automated service tests run only against the independent reference service in `tests/reference_service/`. Validation against deployed services happens outside this repository: by hand in Kit, and in the service's own end-to-end tests, which the service owners run.

The reference service's backends share one in-process state, so replication consistency across backend processes is a service assumption ([design section 12](ovlive-design.md#load-balancing)) that only the service's own end-to-end suite qualifies. Its server-side token expiry takes effect when a test chooses, not after a service's authentication cache; its ingress rejection selects the next new streams, not a method; and its `Ping` rejects an unknown token, which the real service accepts.

## Qualification boundary

The [macOS arm64 source-build workflow](ovlive-build.md#macos-source-sdks) supplies a stock USD 25.11 plugin and Python 3.12 bindings from pinned source SDKs. It is a development configuration; it does not add a qualified release target, a Mac packman package, Kit support or supervised qualification lanes. Its hosted macOS source-build job builds the pinned SDKs and runs direct component, package, sample and staged load-order checks on Apple Silicon. These results and any host integration results must be reported separately from the release gates below.

Seven [qualification gates](ovlive-testing.md#qualification-gates) decide whether a build is releasable. A gate closes when its open items close. The [qualification campaign](ovlive-ci.md#qualification-campaign) lists the runs that produce a release candidate's evidence for them.

| Gate | What the lanes prove today | State | Open items |
| --- | --- | --- | --- |

| Concurrency, deadlocks and memory safety | Every native lane is clean under ASan, UBSan and leak detection with owned USD and OpenSSL suppressions and one disabled registration scope, and under ThreadSanitizer with owned third-party suppressions on the stock USD profile ([sanitizers](ovlive-testing.md#sanitizers)); nested locks are allocation-fault safe; allocation failure before a live layer's first RPC releases everything; a runner watchdog expiry captures every native test driver's thread stacks | No open items; allocation failure inside USD is a stated limitation | — |
| Performance | Storage benchmarks characterize cases and compare two revisions | No per-case budgets | `gate-performance` |
| Error handling and reconnect recovery | The fault matrix passes against the reference service and HTTP/2 reset proxy, including reconnect catch-up aggregates that cover the layer's own acknowledged writes, a paused read that the service ends, reconnects that the service accepts and never answers, server-side token expiry, ingress rejection and TLS through the proxy | Reference lanes pass; rotation qualified by count and by one 60-minute soak on one worker | `gate-long-rotation` |

## CI status

Pull requests and pushes to `main` run repository checks, C++ format checks, foundation and native URI, wire and lock component checks on Linux x86-64, Linux aarch64, Windows x86-64 and macOS arm64 runners. Linux runs component builds with sanitizers off and on; Windows and macOS run with sanitizers off. The plugin, reference-service and writer-campaign lanes run through the standalone [CI profile entry point](ovlive-ci.md#running) on a provisioned worker. The manual release workflow runs the nightly profile for Linux/Windows package selections; no pull-request or scheduled workflow runs these SDK-dependent campaigns (`ci-sdk-lane` in [open items](#open-items)).

The fourth platform, macOS arm64, runs repository/format checks, foundation with four named detached-process cleanup exclusions, and four direct component CTests with sanitizers off in `ci.yml`. The same manual `sdk`/`package` controls in `release-candidate.yml` select work for every platform, including PR head branches without creating candidate tags or releases. The main-only `candidate` choice builds every platform, retaining Mac artifacts separately from the qualified Linux/Windows release assets. For macOS, `build-sdk` builds or validates cached pinned SDKs; the dependent `build-package` job runs ten direct CTests and staged native/Python load-order checks and uploads a checked development archive. All four platforms run foundation/component checks automatically on PR/main events; Linux/Windows package selections require the internal SDK release workers, whose availability is unverified. macOS process-group cleanup handles ordinary workloads and records its boundary. Direct `tools/live/test.py` suite admission is limited to `foundation`, `uri`, `wire-envelope` and `lock-noalloc`; SDK-dependent and reference-service suites require Linux/Windows descendant-tree containment. Detached descendants, forced runner death and full macOS reference-service qualification remain open.

## Known limitations

Creation and authoring use section records for child membership and individual records for time samples. Explicit empty membership/sample maps and nonfinite outgoing sample times fail before issuance with `UNSUPPORTED`. Normal USD removal of the last child or sample erases its field; valid USDA can explicitly author an empty time-sample map, which remains a supported USD value outside this outgoing service representation. Persisted layers containing ordinary derived child fields or ordinary `timeSamples` fields require a separately validated export and recreation; these encoding changes do not migrate service rows or repair conflicting stored values. Native regressions independently retain field and sample rows and rebuild fresh snapshots, covering sample replacement/deletion, seed ordering and structural edits. This bounded storage oracle is source-derived evidence, not execution of either service or deployed-service qualification.

A limitation with open work names its row in the [open items](#open-items); the statements of behavior link the design.

Writers that each first-create the same path before seeing each other converge on the last committed section, and the earlier sections and their contents are deleted (`limit-first-create`). One host turn above 65,536 operations, counting repeated writes to one field or sample once, or above 1,048,576 operations counting every write, roughly 2,500 to 3,000 prims with five authored attributes each, an estimate rather than a measurement, fails the layer with `RESOURCE_EXHAUSTED` and keeps every edit in host content for export ([design section 8](ovlive-design.md#quotas)); an on-host `SdfLayer::Save` ends the turn, so a host that authors in bulk saves between chunks, and Kit command paths that author in one turn are unverified (`kit-rerun`). One update or creation seed also holds at most the live edit service's 99,999 entries, its struct commands, set fields and time samples together, and a child reorder at most 100,000 children; a host turn over them is not sent and fails the layer with `RESOURCE_EXHAUSTED`, keeping every edit in host content for export, and a seed over them is refused before `CreateLayer`, so a larger layer is created from a smaller seed and saved in further turns ([design section 8](ovlive-design.md#quotas)).

Releasing a live layer's last reference closes it and discards the host edits no flush has admitted; the CLOSED status count and the [`host_edits_discarded`](ovlive-diagnostic-catalog.md#discarded-host-edits) diagnostic report them, so a host saves or drains before releasing a layer ([design section 8](ovlive-design.md#capture-and-flush)). An explicit close that leaves the layer alive keeps those edits in host content for export but never sends them. A flush that fails as `UNSUPPORTED` for one of seven reasons (value type, payload offset, identity type change, multi-update, move cycle, time-sample dictionary key, identity realization) posts a USD runtime error on the host that names the layer and reason, plus the path, field and value type when a single operation causes it, and emits the [`flush_unsupported`](ovlive-diagnostic-catalog.md#unsupported-flushes) diagnostic with the reason code; a compiled edit that conflicts with the current scene on replay fails the flush with the typed status only ([design section 9](ovlive-design.md#values-and-limits)).

On the stream, a nonempty header that repeats the stream's current sequence is a protocol violation and fails the layer with `MALFORMED_STREAM` ([design section 12](ovlive-design.md#caught-up-header)); an identical re-delivery across a reconnect is accepted once. A layer whose own incoming work backs up pauses its read and stays `READY` ([design section 12](ovlive-design.md#reconnect)); a layer that falls behind the stream also stays `READY`, and its status's `read_sequence` and `applied_sequence` and the [`apply_lag_entered`](ovlive-diagnostic-catalog.md#apply-lag) diagnostic report the lag ([design section 17](ovlive-design.md#17-operational-status)). Two limits stay hard: an endpoint's pending-byte budget, 1 GiB by default, is shared by every layer, read and intent on it, and a read frame it cannot reserve fails that layer with `RESOURCE_EXHAUSTED`; a peer frame that finds the layer's `max_requests` cap full of retained peer coverage and local intents fails the layer the same way.

An allocation failure inside a public USD call is outside containment: on USD 25.11 it can terminate the process from USD's change-notice delivery or destructors, leave a composed stage out of step with layer data or, inside `SdfLayer::FindOrOpen`'s registry lock, deadlock, and stock `SdfData` layers behave the same. The live backing keeps each storage edit recorded or unapplied, and an allocation failure while a live layer opens, before its first RPC, fails the open with `RESOURCE_EXHAUSTED` and releases everything ([design section 8](ovlive-design.md#failure-containment)); the [allocation probe](ovlive-testing.md#allocation-and-edit-boundary-probes) reproduces the SDK behavior.

Live layers are in-memory only: a host opens each one with `FindOrOpen` or `CreateNew` on its publication context and then inserts it at runtime, and live URIs never appear in loaded or saved content, so no sublayer, reference or payload in a file names one and no live layer references another, directly or indirectly ([design section 1](ovlive-design.md#1-purpose-audience-and-scope)). Composing a live URI that the host has not opened is unsupported: USD opens a layer stack's sublayers in parallel on its worker threads, where `Read` fails with `BUSY`, so such a stage opens with those layers missing and only USD's `Could not load sublayer` warning, which says to open live layers on the host before composing them, reports it.

In the host, a second attached layer for a canonical URI that already has one is rejected with `ALREADY_EXISTS`: one live backing serves each resource ([design section 6](ovlive-design.md#6-usd-integration-file-format-resolver-one-backing-per-resource-bootstrap)). An immediate retry after a failed open waits within its own deadline for the failed backing's admission to retire; a backing pinned to its host is refused at once. A native status callback that throws is disabled and reported by the `callback_failed` diagnostic while its subject stays queryable ([callback failures](ovlive-diagnostic-catalog.md#callback-failures)); a Python status callback's exception stops its subscription and reports through `delivery_status` and `on_error`. A Python host sizes its publication context at about three charged jobs per live layer ([Python guide](ovlive-python.md#publication-context-and-max_pending)); a refused flush job leaves the layer `BLOCKED` with its edits buffered, and a refused publication job fails the layer.

In Kit, the extension does not start on stock public Kit 110.3: a `kit-25.11` package does not bind to its stock USD, and its `omni.usd_resolver` registers a competing `.live` handler. The extension runs only on an internal Kit build with the companion extensions, which are unpublished (`kit-companion`). The extension starts once per Kit process: enabling it again after disabling it in the same process fails with an error that asks for a Kit restart ([Kit guide](ovlive-kit.md#python-modules-and-startup-order)).
